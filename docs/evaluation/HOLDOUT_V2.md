## 作り方

- 1つ目の30ケースと同じ形式です。振る舞い（`holdout_v2_cases.json`）と正解（`holdout_v2_truth.json`）を別のファイルにしています。ラボ（`holdout_v2_lab.py`）は正解のファイルを読みません。
- ケース ID は `holdout-v2-001`〜`030` です。固定の乱数（種 20261122）で並べ替えているので、ID から分類や正解は読み取れません。
- 正解は「判定器が証明できること」ではなく、「サーバーが実際にどう振る舞い、所有者が何を求めているか」で付けています。
- 1つ目のセットになかった応答の形を入れています。特に、**成立にしてはいけない紛らわしい例**と、**新しい規則で誤って不成立にしやすい例**を多めにしています。

| 分類 | 件数 | 内容 |
| --- | --- | --- |
| 紛らわしい例（near_miss） | 12 | マーカーの文字列だけ、所有者が A でマーカー付き、入れ子の B の記録、資源 ID だけ、B の名前付きで識別子なし、識別子も名前もない B のデータ、ログイン画面ではない 200 の HTML、B の名前を含むログイン画面、text/plain の拒否、4 KB を超える本文 |
| 偽装応答・200 の拒否（decoy_200） | 6 | JSON の拒否本文（別の形）、パスワード欄のあるログイン画面、公開一覧、空の配列、「403 Forbidden」の HTML |
| 認可・IDOR | 5 | 成立、拒否、404、本人の資源、所有者の対照が失敗 |
| 公開仕様 | 2 | 所有者の仕様が公開、認証なしで B の名前付きデータ |
| 仕様不足・検査不要 | 2 | 仕様なし、リンクなし |
| 修正後の再確認 | 3 | 修正後に 200 の JSON 拒否、403、識別子のない HTML で B のページが残る |

## 制約（公正さ）

- **作成者は、新しい規則の設計を知った上でこのケースを作りました。** 規則に有利なケースを選ばないよう、規則が誤って不成立にする例（識別子も名前もない B のデータ）や、保留のままになる例を意図して入れています。それでも、作成者と独立した確認の代わりにはなりません。
- **第2の判定者による独立のラベルはまだありません。**
- **人のラベル確認（署名）は未了です。** 署名のひな形は [label_signoff_holdout_v2.template.json](label_signoff_holdout_v2.template.json) です。署名がない間、実行器はこのセットでのループバック以外への送信を拒否します（`require_label_signoff(..., label_set="holdout_v2")`）。
- 1つ目の30ケースとその結果（`comparison.json`）は、比較のためにそのまま残しています。1つ目のうち、改善案の根拠にしたケースは開発・回帰用に移しました（[JUDGE_OWNER_RECORD.md](JUDGE_OWNER_RECORD.md)）。
