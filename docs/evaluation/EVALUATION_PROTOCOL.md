# 診断モデル比較評価の手順（PR #97 基準）

2026-11-21。Claude Sonnet 5.5、Abliterated Model、Abliterated Large v2 のうち、Vulnix の診断ループで「次の検査」を最も正確かつ効率的に選べるのはどれかを、再現できる形で比べるための手順です。

**この段階は DRY RUN だけです。** 外部 API への送信、課金、実サイトへの通信は行っていません。US$5 は将来の評価の総予算の上限であり、実行の承認ではありません。

## 1. 構成

| 部品 | 場所 | 役割 |
| --- | --- | --- |
| 共通の入力 | `aegis/evaluation/request_builder.py` | 診断状態の `planner_view()` から、全方式で同じ入力を作ります。入力は ID と短い語だけで、URL・本文・Cookie・ハッシュ・ケース名・正解は入りません。 |
| モデルごとの形式 | `aegis/evaluation/model_adapter.py` | 共通の入力を各社の API 形式の本文（バイト列）にし、返答を契約の手順に戻します。通信はしません。 |
| 要求プレビュー | `aegis/evaluation/request_preview.py` | 送るはずの本文、共通入力と本文それぞれの SHA-256、設定のハッシュ、トークン上限、最大費用を記録します。 |
| 予算台帳 | `aegis/evaluation/budget_ledger.py` | 全モデルで共有する、評価専用の US$5 の台帳です。 |
| 実行 | `aegis/evaluation/evaluation_runner.py` | 1ケースを1方式で、実際の制御経路（契約 → ProposalRouter → Gateway → 隔離 Worker → 固定判定器）に通します。 |
| 集計 | `aegis/evaluation/metrics.py` | 精度・効率・費用を集計します。95% Wilson 区間も付けます。 |
| 外部通信の遮断 | `aegis/evaluation/network_guard.py` | 評価プロセスでのループバック以外の接続と名前解決を拒否し、件数を数えます。 |
| 操作 | `scripts/run_model_evaluation.py` | `preview`、`compare`、`freeze` の3つのコマンドです。 |

モデルは、検査を ID で選ぶだけです。仮説を「実証済み」にするのは、既存の `diagnosis_judge.py` だけです。モデルの返答に `verdict` などの余分なキーがあれば、返答全体を拒否します。モデルの選んだ検査も、既存の `plan_contract` が受け付けたものしか実行しません。

## 2. 比較する方式

| 方式 | 内容 |
| --- | --- |
| `fixed_l1` | 固定の L1（ルートの GET）だけを行います。 |
| `fixed_rule` | 固定の表で検査を選びます（モデルは使いません）。 |
| `local_model` | ARTEX とローカルの台本モデルで選びます。CI では、ハッシュを固定した実 ARTEX をカーネル隔離して使います。 |
| `model:abliterated-model` など | 実モデルです。**今回は送信していません**（プレビューだけです）。 |

すべての方式で、次を共通にしています。
- 初期観測と所有者の仕様
- 検査カタログ
- `PlanLimits(max_steps=3, max_planner_rounds=2)`
- Gateway、Worker、判定器、終了条件

実モデルの返答は、ARTEX の代役を通して計画項目になります。そのため、後段の契約・承認・実行・判定は、他の方式と同じ経路を通ります。

## 4. 指標

- **主な指標**：次の2つは、目的が違うので別々に集計します。
  - **ケースごとの最終結果**：互いに重ならず、合計はケース数と一致します（`metrics.OUTCOMES`）。分類は、正解、誤検知、誤った確定、保留（妥当）、保留（脆弱性あり）、保留（その他）です。
  - **検出の混同行列**：正例は「他アカウントの読み取りが成立」です。TP、FP、FN（保留も含む）、TN と、Precision、Recall、特異度を、95% Wilson 区間付きで出します。
- **計画・検査**
  - 計画契約の遵守率、無効な返答の率
  - 不要な検査（期待しない検査、同じ検査の繰り返し）、禁止された検査の実行
  - 対象への GET 数、Worker の起動数、計画の周回数
- **段階別**
  - 計画単体（`plan_useful`）：最初の返答が、期待する検査を選び、禁止された検査を含まないか
  - 再計画（`replan_moved_on`）：反証の後、まだ検査できる仮説に移ったか
  - 診断全体：判定器の後の最終状態
- **費用**
  - 入力・出力・推論のトークン、応答時間、モデル費用（公式単価 × 使用量）、予約額、正解1件あたりの費用

30件では統計的な確実性が足りません。区間とケースごとの結果を併記し、誤検知0件でも真の誤検知率が0とは言いません。

暫定の合格基準は次のとおりです。

| 項目 | 基準 |
| --- | --- |
| 契約の遵守 | 98%以上 |
| 不正な検査の実行 | 0件 |
| 誤検知 | 0件を目標 |
| 見逃し | 固定ルール以下 |
| 反証 | 固定ルール以上 |
| Worker 数 | 固定ルール以下を目標 |
| 判断不能 | 該当するケースすべてで適切に保留 |

## 5. 費用と送信の制御

- **単価**：見積もりには、所有者の計画の値と公式の単価（2026-11-21 確認）のうち、高い方を使います。

| モデル | 見積もりの単価 | 公式の単価 | 出所 |
| --- | --- | --- | --- |
| Abliterated Model | $3 / $3 | $1 / $3 | docs.abliteration.ai/pricing.md |
| Abliterated Large v2 | $5 / $5 | $3 / $5 | 同上 |
| Claude Sonnet 5.5 | $2 / $10 | $2 / $10 | Anthropic の料金表 |

- **1要求の最大費用**：入力2,000トークンと出力2,048トークンの上限で計算します。
  - Abliterated Model：$0.012144
  - Abliterated Large v2：$0.02024
  - Claude Sonnet 5.5：$0.02448
- **台帳の初期状態**：`dry_run=true`、`external_calls_enabled=false` です。この状態の台帳は、送信を一切許可しません。
- **予約**：各要求の最大費用を、送信前に予約します。予約はファイルロックの下で行い、fsync してハッシュの鎖でつなぎます。同時に実行しても、US$5 を超える予約はできません。
- **件数の上限**：上限は30ケースです。1ケース・1モデルあたり、診断で2回まで、修正後の確認で2回まで要求できます。自動の再試行はしません。
- **二重送信の防止**：1つの予約で送信できるのは1回だけです。送信の許可は台帳に `send` として先に記録し、同時に実行しても、再起動した後でも、2回目は拒否します。
- **返金しないこと**：失敗、タイムアウト、不正な応答でも予約は戻しません。確認済みの請求額があるときだけ、計上額を予約額以下に下げます。
- **fail-closed**：次の場合は送信しません。
  - 単価が不明
  - トークン上限が不明
  - 台帳が壊れている（改ざん・途中切れ）
  - 入力の見積もりが上限を超える
- **予約と送信は別の許可です**。送信には、承認記録が次のすべてに一致することが必要です。
  - モデル
  - 本文の SHA-256
  - トークン上限
  - 費用の上限
  - 設定のハッシュ（`config_sha256`）

  プレビューの後にモデルの設定やトークン上限を変えると、`config_sha256` が変わり、承認は無効になります。
- **このリポジトリの範囲**：外部への送信機能（ネットワーク転送）は実装していません。テストは、プロセス内の模擬転送（`local = True`）だけを使います。

## 6. 実モデルで評価する前に必要なこと（未実施）

1. 30ケースの正解を、人が確認します（[LABEL_REVIEW_SHEET.md](LABEL_REVIEW_SHEET.md)）。人の署名（`docs/evaluation/label_signoff.json`）には、ラベルのファイルの SHA-256 を含めます。署名がない場合、またはラベルのファイルが変わった場合は、実行器がループバック以外への送信を拒否します（`require_label_signoff`）。
2. 送信の当日に、公式の単価・モデル ID・API の仕様を確認し直します。特に次の2点です。
   - Large v2 の推論トークンが出力として請求されるか
   - Claude の `output_config.format` と effort の組み合わせ
3. プロバイダーのトークン数え上げで、入力が2,000トークン以下であることを確認します。
4. 送る本文の SHA-256 の一覧（`requests.jsonl`）、モデルごとの上限費用、送信内容を示し、所有者の承認を1回ずつ受けます。
5. 承認された本文だけを送る転送処理を、別の PR で追加し、レビューを受けます。

採用の方針は次のとおりです。
- 1つのモデルで十分なら、そのモデルを採用します。
- Claude と Abliteration で得意な条件に明確な差がある場合だけ、条件ごとに振り分けます。
