## 結論

- **検査の選び方が原因のケースは、0件です。** どのケースでも、期待した2つの検査（認証なしの GET と、別アカウントでの読み取り検査）が実行されました。禁止された検査や不要な検査はありません。
- 残りの誤りの原因は、次の3つです。
  - 判定規則の仕様上の限界
  - 観測した情報の不足
  - 所有者本人の対照（比較の基準）の不足
- そのため、**モデルを替えても、この5件は改善しない見込みです。**

## 改善案

いずれも提案だけで、実装していません。

### 案1：対照と比べて、B の記録がないことを確かめる（不成立の判定を追加）

- **観測の項目**：`check_attrs` に、`owner_identifiers_present` を加えます。これは、A への応答本文に、B 本人の対照で得た資源 ID と機密マーカーのどちらかが含まれるかを示します。
- **新しい規則**：次の条件がすべてそろうとき、「不成立（`owner_record_absent`）」とします。
  - 対照が成立している
  - 状態コードが 200
  - B の識別子がどこにもない
  - 応答が要求者自身の資源でもない
- **期待できる効果**：holdout-001 と 013 が正解になります。
- **誤検知への影響**：この規則は「不成立」しか作らないので、誤検知は増えません。
- **危険**：見逃しが増える可能性があります。B のデータを識別子なしの形で返すサーバーを「不成立」にしてしまうためです。これを抑えるには、本文が JSON で、B のアカウント名も含まない場合に限ります。

### 案2：要求の身元と、対照と一致する記録で成立を判定する（成立の判定を広げる）

- **新しい条件**：応答本文の `caller_account` の自己申告ではなく、次の3点を条件にします。
  - Worker が A として送ったことを確認済み（`request_headers`）
  - 応答の資源 ID と機密マーカーが、B 本人の対照と一致する
  - 所有者が B
- **期待できる効果**：holdout-030 が正解になります。
- **誤検知への影響**：紛らわしい例（マーカーの文字列だけが入っている、所有者が A）は、資源 ID の一致がないため、成立になりません。
- **影響範囲**：変更する場所は `aegis/evidence.reproduction_verdict` で、所見の「実証成功」に直結します。そのため、別の PR に分け、独立したレビューと、紛らわしい例の回帰テストを必須にします。

### 案3：認証なしの応答も、対照と比べる

- **変更内容**：L1 の GET の結果にも、`owner_identifiers_present` を残します。
  - B の識別子がある → 成立
  - 200 で、識別子が一切なく、JSON の拒否本文・HTML・公開一覧のいずれか → 不成立
  - それ以外 → 判断不能のまま
- **期待できる効果**：
  - holdout-001、010、013、017 は不成立として正解になります。
  - holdout-014（識別子のない B のデータ）は判断不能のまま残ります。
- **誤検知への影響**：「成立」には識別子の一致が必要なので、誤検知は増えません。

## 評価の公正さのための注意

上の改善案は、**この未見30ケースを見て作りました**。実装する場合は、次のようにします。

1. 根拠になったケース（001・007・010・013・014・017・029・030）を回帰用に移します。
2. 判定器を変えた後の最終評価には、新しく作る未見のケースを使います。
3. 実モデルの比較は、判定器を固定した状態で行います。判定器が変わると、モデルの差と判定器の差が混ざるためです。
