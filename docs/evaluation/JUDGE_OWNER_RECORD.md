## 1. 変えたこと

### 1.1 新しい規則（どちらも「不成立」しか出しません）

| 規則 ID | 仮説 × 検査 | 条件（すべてそろうときだけ） |
| --- | --- | --- |
| `owner_record_absent` | 他アカウントの読み取り × `l2_idor` | 所有者 B 本人の対照が成立／再現は成立していない／A への応答が 200／要求者自身の資源ではない／**B の対照で得た識別子（資源 ID・機密マーカー）が応答のどこにもない**／**B のアカウント名もない**／本文を最後まで読めている／本文が **拒否の形をした JSON**（`error`・`message` などの拒否のキーだけで、拒否の語や 401・403 を含むもの）、または HTML のログイン画面・拒否画面 |
| `owner_record_absent_without_auth` | 認証なしの露出 × `l1_http_probe` | 応答が 200／**ラボの所有者の識別子（`res_b_001`・機密マーカー）とアカウント名（`acct_B`）が本文にない**／本文を最後まで読めている／本文が拒否だけの JSON、またはログインのフォームだけ・拒否の見出しだけの HTML（§5・§5.1） |

- 規則の順番は変えていません。所有者の仕様が「公開」なら `intended_public`、対照の失敗は `control_failed`、再現の成立は `cross_account_read`、401・403・404 は `denied`、本人の資源は `own_resource_only` が、これまでどおり先に決めます。新しい規則は、これまで「判断不能」になっていた場合の一部だけを「不成立」にします。
- **「成立」を出す規則は追加していません。** 案3の「B の識別子がある → 成立」は実装していません。認証なしの応答に B の識別子があっても、これまでどおり「判断不能（`answered_without_auth_unverified`）」です。成立の判定を広げる変更（案2を含む）は、所見の「実証成功」に直結するため、別の PR で独立したレビューを受ける対象として残しています。
- 識別子は、Worker が監査済みの結果に書いたものだけから読みます。`l2_idor` では、同じ結果の中の B 本人の対照の応答（`control_response`）の資源 ID と機密マーカー、アカウント名（`resource_owner`・`caller_account`）を使います。プランナーやモデルの出力は使いません。`l1_http_probe` には対照の要求がないため、ラボの Worker が対照として受け入れる固定の値（`res_b_001`、機密マーカー、`acct_B`）と比べます。診断ループは登録済みのローカル検証ラボでしか動かないので、この値は常にその所有者のものです。
- 識別子とアカウント名は、大文字と小文字を区別せず、HTML の実体参照・% エンコード・JSON のエスケープを戻した形でも探します。見つかったら「ある」とし、規則は働きません（見逃しを増やさない側に倒しています）。
- 本文を最後まで読めていないときは比べません。`l2_idor` では Worker が残す 4,096 文字に達した本文、`l1_http_probe` では Content-Length と読んだ長さが合わない本文（Content-Length がなければ 4,096 バイトに達した本文）です。
- 「ログイン画面」は、パスワード欄があるか、「sign in」「log in」などの語を含む `<form>` がある HTML です。フォームの外にあるログインのリンクだけでは該当しません。「拒否画面」は、`<title>` か `<h1>` に「forbidden」「access denied」などがある HTML です。それ以外の HTML とテキストは比べません。

## 5. 見逃しを避けるために条件を締めた（レビューでの判断）

最初の実装では、本文が JSON なら、どんな JSON でも「B の記録がない」と判定できました。そのため holdout-v2-006 で、**脆弱なケースを「不成立」と確定**してしまいました。このケースは、B のデータから識別子と名前を除いた JSON です。

セキュリティ診断では、見逃しを「安全」と言い切る誤りは、判断を保留するよりも重く扱います。そこで、JSON は **拒否の形をしたもの（`error`・`message`・`status` などの拒否のキーだけからなり、拒否の語や 401・403 を含むもの）** に限りました。データの形をした JSON（`json_data`）は、識別子がなくても判断しません。

| 指標（新しい未見ケース） | 変更前 | 締める前 | **締めた後** |
| --- | --- | --- | --- |
| 他アカウントの読み取り：正解 | 14 | 19 | **17** |
| 誤検知 | 0 | 0 | **0** |
| 誤った確定（脆弱なのに不成立） | 0 | 1 | **0** |
| 認証なしの露出：正解 | 20 | 25 | **23** |
| Worker の起動・GET の回数・費用 | 94 / 116 / $0 | 同じ | 同じ |

**公正さについて：** 条件を締める判断は、v2 の結果（holdout-v2-006）を見たあとに行いました。そのため、v2 の数値は、この判定器の偏りのない推定値ではなくなりました。偏りのない最終評価には、判定器を固定したあとで作る、別の未見ケース（v3）が必要です。v3 のラベルにも、人による確認と署名が必要です。v2 のラベルの署名もまだありません。実モデルとの比較は、送信の承認を待っています。

### 5.1 独立レビューを受けて、さらに締めた点（2回目）

独立レビューで、まだ「脆弱なのに不成立」と判定できる形が見つかりました。次のように締めました。

- **データを包んだ JSON**：たとえば `{"ok":true,"detail":{…B のデータ…}}` や `{"error":"denied","detail":"<B の記録の base64>"}` です。拒否の形をした JSON と見なすのは、次のすべてを満たすものだけにしました。
  - 値がすべて短いスカラー値である（`errors` は、`code` と `message` だけを持つ要素の並び）。
  - `ok` も `success` も true ではない。
  - 拒否の語が、エラーの項目の値にある。
- **ログイン画面や拒否画面に見えるだけのページ**：たとえば、パスワード変更のフォームがある本人のページ、「Last login」を含むフォーム、題名に unauthorized を含む一覧のページです。これらと区別するため、次の条件を設けました。
  - ログイン画面：フォームが1つだけで、パスワードの欄と利用者名の欄（またはサインインの語）があり、フォーム以外の表示がほとんどない（300文字以内）。パスワード変更のフォームは除く。
  - 拒否画面：フォームがなく、題名か見出しが拒否で、ほかの表示がほとんどない。
- **JavaScript でエスケープした識別子**（`res\u005fb\u005f001`）：元の文字に戻して照合し、「識別子あり」とします。
- **本文の切り詰め**：L2 の Worker の結果に `response_truncated` を加えました。判定器は、この値が `false` のときだけ本文を最後まで読めたものとして扱います。この値がない古い結果は、最後まで読めていないものとして扱います。

これらの形は、すべて回帰テスト `TestEnvelopesAndPagesThatCarryData` で確かめています。締めた後の結果は次のとおりです。

- 新しい未見ケース（v2）：正解17、誤った確定0、誤検知0。§5 の表から変わっていません。
- 1つ目のセット（参考値）：正解26、誤った確定0、誤検知0。
- 1つ目のセットの holdout-001（パスワード欄のない最小の「Sign in」フォーム）は、ログイン画面と見なさず、判断不能に戻りました。
