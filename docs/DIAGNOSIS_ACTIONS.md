# 診断ループの操作（PR-C）

2026-11-22。[DIAGNOSIS_UI_IMPLEMENTATION_PLAN.md](DIAGNOSIS_UI_IMPLEMENTATION_PLAN.md) の PR-C です。PR-B（[DIAGNOSIS_UI_PANEL.md](DIAGNOSIS_UI_PANEL.md)）の画面に、次の4つの操作を加えます。

- 診断の開始
- 所有者の仕様の入力
- L2 検査の承認（1手順ずつ）
- 修正後の確認の開始

**対象は、登録済みのローカル検証ラボだけです。** 実サイトや所有確認中のサイトでは、どの操作のルートも存在しません（404）。外部モデル・有料 API・実サイトへの通信はありません。

## 1. 権限

権限はサーバー側で、要求のたびに確かめます。画面に出るボタンは、GET の `viewer.permissions` に従います。ただし、ボタンの有無は判断に使いません。

| 権限 | 使える操作 | 対応するサービスのロール | 組織のロール |
| --- | --- | --- | --- |
| `diagnosis:read` | 表示 | （メンバーなら誰でも） | owner / admin / runner / approver / viewer |
| `diagnosis:request` | 開始、修正後の確認 | operator | owner / admin / runner |
| `asset:specify` | 所有者の仕様 | admin | owner / admin |
| `diagnosis:approve_l2` | L2 の承認 | approver | owner / approver |

どの操作でも、次を順に確かめます。

1. ログイン（401）
2. CSRF（403）
3. 組織のメンバーであること（403。監査ログに `tenancy.access_denied` を記録）
4. 閲覧者でないこと（403）
5. 送信の直前に、ログインと所属をもう一度確かめる（`_dispatch`）
6. 操作の権限（403 `permission_denied`）
7. 対象が登録済みラボであること（404）
8. 緊急停止・一時停止中でないこと（409）
9. 要求時点の権限（403 `authority_revoked`）

診断ループの実行中は、依頼者の権限を手順ごとに確かめ直します（`live_request_authority`）。ログアウトしたり組織から外れたりすると、ループは止まります。

診断の範囲と有効期限は、既存の Gateway が手順ごとに確かめます（`_ensure_active_window_locked`）。

**依頼者と L2 の承認者は、同じ人にできません。** これは3か所で確かめています。

- 承認の API（403 `self_approval`。監査ログに `diagnosis.approval_denied` を記録）
- 既存の `execute_artex_item`（計画を依頼した本人は承認できない）
- 画面（依頼者には承認のボタンを出さない）

自分で登録したアカウントは、L2 を承認できません（既存の `/request-l2` と同じ扱い）。

## 2. API

```
POST /api/assessments/{id}/diagnosis/start        {}                                      diagnosis:request
POST /api/assessments/{id}/diagnosis/owner-spec   {"target_ref": "T2", "requirement": ...} asset:specify
POST /api/assessments/{id}/diagnosis/approve      {"item_id": "..."}                      diagnosis:approve_l2
POST /api/assessments/{id}/diagnosis/fix-check    {"owner_specs": {...}}（省略可）          diagnosis:request
```

- `requirement` は、`authentication_required`（認証必須）か `public`（公開）のどちらかです。
- `fix-check` の `owner_specs` を指定できるのは、`asset:specify` を持つ人だけです。
- `GET .../diagnosis` は、PR-B の表示に次の2つを加えます。
  - `operation`：診断ループの実行状態。依頼者、状態、承認待ちの項目、終了理由です。結果は含みません。
  - `viewer`：その要求の時点で有効なロールから計算した、読む人の名前と権限です。
- SSE の `diagnosis.updated` は全員に同じ内容を送るため、`viewer` を含みません。

## 3. 流れ

1. **開始**：診断を開き（`diagnosis.opened`）、L1 の初期観測を取ります（`observe_lab_root`）。そのあと、決まった規則で仮説を作ります（`propose_hypotheses`）。
2. 所有者の仕様が必要な対象（ラボのアカウント資源）に、この世代の仕様がなければ、`awaiting_spec`（仕様待ち）で止まります。
3. **仕様の入力**：監査ログに記録してから反映します（`DiagnosisState._commit`）。仕様待ちの診断があれば、依頼者の権限を確かめ直してから、診断ループを続けます。
4. 診断ループ（`AdaptivePlanRunner`）は、L1 の検査を自動で行います。L2 の手順では `waiting_approval`（承認待ち）で止まります。
5. **承認**：その手順のための1回限りの nonce に対して、`diagnosis.l2_approved` を監査ログに記録します。そのあとに限り、ループが承認者の名前とロールで、その手順を1回だけ実行します（隔離された Worker）。
   - ループが承認を受け取る時点で、承認者の権限をもう一度確かめます。
   - 承認されないまま時間切れになった場合（`VULNIX_DIAGNOSIS_APPROVAL_TIMEOUT`、既定 900 秒）や、停止・リセットがあった場合、L2 は実行しません（`l2_approval_missing`）。
6. **修正後の確認**：修正前に実証された所見（`evidence_status == "proven"` で、支持された仮説があるもの）がある場合だけ始められます。
   - 新しい世代を作り、初期観測を取り直します。
   - 仕様は引き継ぎません。新しい世代で入力し直します。
   - L2 の承認も新しく必要です。

### 仕様の変更が判定に与える影響

固定の判定は、仮説と同じ世代の、最新の仕様を使います（`diagnosis_judge._requirement`）。このため、次のように扱います。

| 場合 | 扱い |
| --- | --- |
| まだ仕様がない | 記録します |
| 同じ世代・同じ値をもう一度送った | 409 `already_accepted`（同じ対象・世代への同じ操作） |
| 違う値で、その仕様を根拠にした判定がまだない | 記録します（最新の値が使われます） |
| 違う値で、その仕様を根拠にした判定がすでにある | 409 `needs_new_generation`。判定を書き換えないよう、修正後の確認（新しい世代）で入力します |
| 診断ループの実行中 | 409 `loop_running` |

## 4. 二重送信の防止

`Idempotency-Key`（16〜128文字の英数字・`-`・`_`）を必須にしています。キーがなければ 400 です。Next.js のプロキシは、この形のキーだけを転送します。

要求は、次の順で受け付けます。

1. 監査ログに `diagnosis.request_accepted` を記録します。
2. 要求の記録（`data/<組織>/diagnosis_requests.json`、0600）をディスクに書きます。

どちらかが失敗した場合は 503 で、何も始めません。そのキーは使われていない扱いになり、同じ要求を送り直せます。

| 場合 | 応答 |
| --- | --- |
| 同じキー・同じ要求（操作・内容・送った人） | 保存した結果を返します（`replayed: true`）。何も実行しません |
| 同じキー・違う要求 | 409 `idempotency_key_reused` |
| 同じ組織・対象・操作・世代に、別のキーで送った | 409 `already_accepted` |
| 診断ループの実行中に、開始または修正後の確認を送った | 409 `loop_active`（1つの評価で同時に動く診断ループは1つだけ） |
| 診断ループの実行中に、ARTEX 計画の作成や項目の直接実行を送った | 409（ループの L2 を二重に実行しないため） |

排他の範囲は次のとおりです。範囲は組織ごとのファイルに記録します。

- 仕様：`owner_spec:<diag>:<世代>:<対象>:<値>`
- 修正後の確認：`fix_check:<diag>:<世代>`
- 承認：`approve:<項目>:<nonce>`

拒否された要求は、範囲を占有しません。

**再起動・タイムアウト：**

- 診断ループの途中でサーバーが止まった場合、その診断ループは `interrupted`（中断）として残り、自動では再開しません。
  - 正常に停止した場合は、`close()` が記録します。
  - 強制終了した場合は、次の起動時にファイルから判断します。
- 同じキーでの再送は中断の記録を返すだけで、何も実行しません。
- ARTEX 計画の項目はメモリにしかないため、再起動の後に同じ手順の Worker が動くことはありません。
- 停止したサービスは、ファイルを二度と書きません（次のプロセスの記録を上書きしないため）。

## 5. 修正の前後の比較

PR-B の「③ 修正の前後」に、次の3つを加えました。

- 各側の検査結果の監査ハッシュ
- その検査結果が再現について示したこと（「再現 成立」→「再現せず」）
- その手順の検査結果を証拠に持つ所見と、その所見の現在の判定（例：`f_idor` 現在の判定 再現せず）

所見は、手順の検査結果の監査ハッシュで結び付けます。推測では結び付けません。

## 8. レビューで残った3件の解消（マージ前）

各項目について、修正前のコードでは失敗する競合テストを追加しました。修正を一時的に外すと、そのテストが失敗することも確かめています。

### 8.1 L2 承認者の権限を、Worker の起動直前に確かめ直す

ループは、承認を受け取ると、その1手順だけに使える権限（`_step_authority`）を作ります。これを、既存の Gateway が Worker を起動する直前に呼ぶ確認（`AssessmentService._late_launch_guard`）に渡します。`execute_artex_item` が始まるときにも、同じ権限を確かめます。

確かめる内容は次のとおりです。

- 依頼者のログインと組織への所属
- 承認者のログイン、組織への所属、approver の権限
- 依頼者と承認者が別の人であること
- 承認の nonce（その手順のために発行したもの）、対象の項目、診断と世代、実行の世代
- 承認の期限（`VULNIX_DIAGNOSIS_APPROVAL_VALID`、既定 300 秒）
- ループが実行権を持っていること、停止中でないこと

起動の間は、依頼者と承認者の両方の lease を持ちます。そのため、ログアウトや組織からの除外は、起動が終わるまで待ちます。どれかが失効していれば `PolicyError` となり、Worker は起動しません。

テスト：

- `test_the_approver_revoked_right_before_the_worker_starts_launches_nothing`：起動直前の確認の中で、承認者を失効させます。
- `test_an_expired_approval_launches_nothing`

### 8.2 手動の ARTEX と診断ループの実行権を、同じロックで取る

`AssessmentService._exec_owner` が実行権です。どちらの側も、サービスのロックの中で実行権を確かめ、取ります。

- 診断ループ：開始や修正後の確認でジョブを作るとき、サービスのロックの中で次を同じ区間で行います。そのため、確認と取得の間に割り込まれることはありません。
  - 実行中の手動の項目がないこと（409 `item_running`）を確かめる
  - 実行権を取る
- 手動の操作：`plan_with_artex` と `execute_artex_item` は、次の時点で実行権を確かめます。
  - 計画を始めるとき
  - 計画の項目を差し替えるとき
  - 項目を実行状態にするとき（`_claim_artex_item_locked` と同じ区間）

  手動の操作（`exec_owner=None`）は、ジョブが実行権を持つ間は拒否します（`ExecutionConflict`、409）。ループのランナーは、自分のジョブの ID を渡します。

- 実行権は、次のときに解放します。
  - ジョブが終わったとき
  - 期限が切れたとき
  - 停止したとき
  - リセットしたとき
  - サーバーを閉じたとき
- ルートで行っていた確認（確認と実行の間に隙があった）は削除し、サービスでの確認に一本化しました。

テスト：

- `test_a_manual_artex_run_cannot_take_a_step_the_loop_holds`
- `test_a_manual_run_checked_before_the_loop_started_is_refused_at_its_claim`：手動の実行がすべての確認を通った後、項目を実行状態にする直前で止めます。その間に診断ループを開始します。
- `test_a_running_manual_item_keeps_the_loop_from_starting`

### 8.3 操作の永続状態と HTTP 応答を分ける

操作の結果は、要求の記録として保存します（再送では、その記録を返します）。そのうえで、応答を返す直前に権限をもう一度確かめます（`_deliver_diagnosis_op`）。確かめるのは、その操作の権限そのものと、承認の場合は approver の権限です。

失効していれば、401 または 403 を返します。このとき返すのは、受け付け済みかどうか（`committed`）だけです。ジョブ、項目、証拠は返しません。

- 同じキーでの再送は、記録を返す前に、いまの権限で操作の権限を確かめます。失効した人には何も返しません。権限が戻った人には、保存した結果を返します（`replayed`）。どちらの場合も、もう一度は実行しません。
- 画面は、`committed` のときに「操作そのものは受け付け済みです（もう一度は実行されません）」と表示します。
- テスト：`test_authority_lost_right_after_the_operation_withholds_the_result_and_never_reruns`。操作が保存された直後、応答の前に組織から外します。

### 8.4 仕様待ちが資源を占有しないこと

仕様待ちの間、スレッドも Worker も動きません。ランナーのスレッドは、仕様がそろってから初めて作ります。

- 仕様待ちの状態は、`spec_since` と一緒にファイルに保存します。
- 次の場合、ジョブを終えて実行権を解放します。
  - 期限切れ（`spec_timeout`）
  - 停止・リセット（`stopped_or_reset`）
  - 再起動（`interrupted`）
- テスト：`test_waiting_for_the_owner_holds_no_thread_and_no_worker`。スレッドがないこと、Worker が増えないこと、ファイルに保存されていること、再起動で中断になり実行権が解放されることを確かめます。期限切れと停止は `test_a_job_waiting_for_the_owner_ends_on_timeout_and_on_stop` で確かめます。

### 8.5 Worker の実行中の権限失効と緊急停止

結果を記録するときにも、その手順の権限を確かめます。これは既存の `_exec` の確認で、PR-C ではここで使う権限を、依頼者と承認者の両方を見る手順ごとの権限にしました。どちらの場合も、結果は採用しません。

| Worker の実行中に起きたこと | 扱い | テスト |
| --- | --- | --- |
| 緊急停止 | 結果を採用しない（判定も所見もない）。計画は CANCELLED または FAILED | `test_an_emergency_stop_while_the_l2_worker_runs_adopts_nothing` |
| 承認者がロールや組織の所属を失った（通常のロール変更を含む） | 結果を破棄し（`result.discarded` を記録）、計画は REJECTED。判定も所見もない | `test_the_approver_losing_the_role_while_the_worker_runs_discards_its_result` |
| 依頼者の権限が失効した | 同じく破棄する（既存の規則） | `tests/test_diagnosis_loop.py` の `test_revocation_while_the_worker_runs_discards_the_result` |

このように、権限の失効と明示的な停止のどちらでも、安全側（結果を採用しない）に倒します。通常のロール変更でも結果を残さないので、その手順は、新しい承認を得てやり直す必要があります。

### 8.6 永続化の境界での強制終了

各境界で強制終了した瞬間のファイルを、新しいプロセスで開きます。そのうえで、クライアントが同じキーで送り直します（`TestCrashAtEachBoundary`）。

| 強制終了した時点 | 再起動後 |
| --- | --- |
| 承認の要求を監査ログに書いた後、要求の記録を保存する前 | 記録がないので、新しい要求として扱います。診断ループはプロセスと一緒に終わっているため、409 `not_waiting`。Worker は動きません |
| 要求の記録を保存した後、承認を渡す前 | 診断ループは `interrupted`。再送には、保存した記録が答えます。Worker は動きません |
| L2 の Worker を起動する時点 | 診断ループは `interrupted`。承認・開始・仕様の再送は、すべて保存した記録を返します。新しいプロセスでは Worker が1回も動かず、計画の項目もないので、手動でも実行できません |

## 9. 残っているリスク

- 期限切れは、評価を読み書きしたときに判定します。誰も触らない間はファイル上で仕様待ちのままですが、スレッドも Worker も使いません。次に触ったとき、または再起動のときに終わります。
- Worker の実行中に承認を無効にする専用の操作（承認の取り消し）はありません。実行中の手順を止める明示的な操作は、緊急停止です。緊急停止では、その手順の結果を採用しません（判定も所見も残りません。`test_an_emergency_stop_while_the_l2_worker_runs_adopts_nothing`）。
- 承認待ちの通知（メールやチャット）はありません。画面と SSE だけです。
- 承認の時間切れ、承認の有効期限、仕様待ちの期限は、環境変数で一律に決めています。組織ごとの設定はありません。
- 要求の記録は、組織ごとに最大 500 件です。古いものから消えます（進行中の要求は消しません）。
