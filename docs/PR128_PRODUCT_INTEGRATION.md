## 実 Cloud Run トークンの受入手順（未実施）

所有者が許可した STG の登録済み HTTPS 443 ホストと専用サービスアカウントを用意する。IAM の Cloud Run 呼び出し用 audience と、Vulnix が発行した `urn:vulnix:cloud-run-proof:...` audience を取り違えない。組織管理者がサービスアカウントの `sub` を登録し、依頼者が5分の challenge を発行する。STG の head に指定 meta を一時掲載し、Google が署名した実 ID トークンを指定 audience で発行する。トークン値・秘密鍵・チャレンジ値はログや報告に記載しない。所有確認成功後、署名・issuer・audience・sub・期限と各 DNS 解決 IP の TLS/meta 一致を確認し、別途範囲確定を行う。失敗、期限切れ、別主体、別ホスト、再送、DNS 変更を検査し、診断権限が付かないことを確認する。実トークンの発行方法と audience 互換性は STG で確認するまで未確認と扱う。

## STG 受入試験計画（未実施）

所有者が許可した専用ホスト、通信元、時間帯、停止連絡先、禁止パス、テストアカウント、費用上限を先に記録する。専用組織で登録から所有確認、範囲確定、読み取り専用 L1、候補、別人承認、隔離 L2、報告、修正後の再診断まで画面で実行する。各段階で実際の接続先 IP、監査イベント、Worker の隔離状態、停止後の通信ゼロ、別組織の拒否を照合する。想定外の通信や隔離失敗時は緊急停止し、失効と残存 Worker を確認する。本計画は実サイトへの通信許可ではない。

## 診断精度の合格基準

事前に陽性・陰性・通常の500・認証エラー・説明文だけの SQL 文言・不完全応答・証拠不足を含む固定ラボ事例を凍結する。カテゴリ別に真陽性、偽陽性、真陰性、偽陰性、判定保留を数え、証拠IDと実際の HTTP 観測を人が照合する。HTTP ステータスだけで実証済みにせず、エラーベース SQLi が再現しなくても SQLi 全般の不存在とは書かない。リリース前に許容する偽陽性率・取りこぼし率を所有者と決め、未知の事例で再評価する。現在の模擬ラボ結果だけで実サイトの診断精度は保証できない。

## 永続ストレージ移行とロールバック

現行 SQLite のチャレンジ原子消費は同一ファイルを使うプロセス間に限る。Cloud Run の独立したインスタンス間では共有されない。本番の水平分散前に、共有トランザクションストアへ主体登録・バージョン・チャレンジ・発行制限を移し、署名付き所有台帳・監査ログ・失効状態もインスタンス間で一貫させる。移行時は新規発行を止め、既存チャレンジを期限切れにし、登録と失効の整合性を検証してから切り替える。複数インスタンス同時消費、再起動、障害復旧、失効伝播を試験する。

障害時は新規診断を停止し、チャレンジと診断範囲を失効する。旧版へ戻す前に新旧双方の所有証明と失効記録を照合し、不一致なら再所有確認を要求する。コードのロールバックだけで診断権限を復活させない。監査ログと停止記録を保全し、再開は管理者の確認後に行う。

## 現在のリリース阻害要因

- 実 Cloud Run トークンの audience 互換性と STG 全工程は未確認。
- Cloud Run 複数インスタンス用の共有永続ストレージと台帳・失効同期は未実装。
- 新規利用者が単独で信頼済み別人承認者を用意できない。プラットフォーム管理者によるアカウント作成が必要。
- 所有確認から実サイトの L2、報告、再診断までを一つの画面導線で通す受入試験は未実施。診断ループ操作 API は登録済みローカルラボ専用。
- 実サイトの診断精度と運用上の許容値は未確認。
