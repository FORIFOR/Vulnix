# ARTEX 関連の攻撃手法（TTP）と Vulnix の対応状況

2026-11-23。対象は main `3f59eeb`。

この文書は、Vulnix が**いま本当に見つけて実証できる脆弱性**を、公開された攻撃手法と照らし合わせたものです。

- 書いてあるのは、コード・テスト・評価記録で確かめたことだけです。
- テストが通ったことは、実サイトで脆弱性を見つけられる証拠ではありません。そのため、実証の段階を分けて書いています。

**ARTEX とは**：オープンソースの、LLM を使ったエージェント型の侵入テストのフレームワークです。

- 計画を立てるエージェントと実行するエージェントが、事実・所見・目標のグラフを共有します。
- 独自のモデルは持たず、外部の LLM を呼び出します。
- 複数の攻撃グループが、侵入に転用しています（C2、F）。

Vulnix も、この ARTEX を「計画の提案」に限って組み込んでいます。実行の権限は Gateway だけが持ちます。

## 3. 現在の実装とのギャップ

1. **優先5分野のうち、IDOR 以外は、ラボも検査もありません。**
   - 対象：SAML、XXE とメタデータ、`is_admin` の一括代入、JS に残った秘密情報、鍵の偽造、クラウドの権限
   - 該当する手法のほとんどは、表で ① から ✗ です。
2. **Worker が送れるのは GET と HEAD だけです。**
   - SAML の ACS（POST）、XXE（XML の本文）、一括代入（POST）を検証するには、決められた本文を送れる必要があります。
   - これは Worker の能力の境界を変えることになるため、所有者の判断が必要です。
3. **ARTEX の提案は、5種類の検査にしか対応付けられません**（`artex_bridge.py:99-119`）。それ以外の提案は「助言のみ」になります。
4. **モデルの評価と Worker の評価が、分かれていません。**
   - これまでの holdout v1〜v5 は、IDOR の判定器を応答の形を変えて試したもので、モデルが検査を選ぶ力は測っていません。
   - ラボでの実証は、主に検査ごとの単体テストに頼っており、検査ごとの検出率と誤検知の率を出していません。
5. **ARTEX 自体の隔離に、既知の隙間があります**（`integrations/artex/README.md:44-46`）。`/usr` などが読めること、中継プロセスに seccomp がかかっていないことです。資料にあるとおり、ARTEX は実際の攻撃に使われているので、この隙間は優先して塞ぐべきです。

## 4. シナリオ（隔離ラボ、模擬データのみ）

すべてのシナリオに共通する前提です。

- 対象は `lab.test` の模擬サービスです。模擬のアカウント、模擬の IdP、模擬のクラウド、模擬の秘密情報だけを使います。
- 実際の IMDS（169.254.169.254）は、これまでどおり送信先として拒否します。
- どの検査も、決められた要求を1回だけ送ります。

### S1：署名のない SAML アサーション（T1606.002）

| 項目 | 内容 |
|---|---|
| 模擬データ | 模擬の SP と IdP。アカウントは `mock-user`。「署名を確かめる」と「確かめない」の2つの設定を用意する |
| 安全な検証 | `mock-user` の主体だけを持つ、署名を外したアサーションを、模擬 SP の ACS に1回 POST する |
| 期待する証拠 | 模擬 SP が `mock-user` のセッションを発行したことを示す印（`VULNIX_LAB_SAML_ACCEPTED`）と、応答の要約、監査ログのハッシュ |
| 修正の方法 | 応答とアサーションの両方の署名を必須にする。IdP の証明書を固定する。署名のない応答を拒否する |
| 合格の基準 | 「確かめない」設定で実証済み、「確かめる」設定で再現しない。この組を10条件以上試して、誤検知0、取りこぼし0 |

### S2：XXE と模擬のメタデータ（T1190、T1552.005）

| 項目 | 内容 |
|---|---|
| 模擬データ | XML を受け付ける模擬のエンドポイントと、模擬の IMDS（ラボ内の `imds.lab.test`。v1 はトークンなし、v2 はトークンが必要）。中にあるのは模擬のロールの資格情報だけ |
| 安全な検証 | (a) XXE：外部エンティティが**ラボ内のカナリア URL** を指す XML を1回送り、カナリアに取りに来たかどうかを見る。(b) IMDS：模擬の IMDS に、トークンなしで1回 GET する |
| 期待する証拠 | カナリアへのアクセスの記録（どの要求から来たか）。模擬の IMDS が v1 で応答したこと。資格情報の本体は記録しない |
| 修正の方法 | XML パーサーで DTD と外部エンティティを無効にする。IMDSv2 を必須にし、hop limit を 1 にする |
| 合格の基準 | 脆弱な設定と修正済みの設定を見分け、誤検知0。実際の 169.254.169.254 への送信が0件であることを監査ログで確かめる |

### S3：認可の回避（IDOR と一括代入、T1190、T1136）

| 項目 | 内容 |
|---|---|
| 模擬データ | 既存の access_control_lab に加えて、模擬の登録 API を用意する。`is_admin` を受け入れる版と、無視する版 |
| 安全な検証 | IDOR は既存のとおり。一括代入は、模擬アカウントの登録を1回 POST し、そのアカウントのロールを1回 GET する。検証のあとで、そのアカウントを削除する |
| 期待する証拠 | 作ったアカウントの `role=admin`、要求と応答のハッシュ |
| 修正の方法 | 受け付ける項目を許可リストで決め、ロールはサーバー側だけで決める |
| 合格の基準 | 既存の IDOR の基準（v5 で誤検知0）を保つ。一括代入は、脆弱な版と修正済みの版で誤検知0、取りこぼし0 |

### S4：認証情報の悪用（T1552.001、T1606）

| 項目 | 内容 |
|---|---|
| 模擬データ | 模擬の SPA の JS バンドル（模擬の管理者パスワードと、模擬の API キーが入ったもの）。模擬の JWT サービス（廃止したはずの鍵も受け入れる版と、受け入れない版） |
| 安全な検証 | (a) JS：読み取りだけ（GET）で、秘密情報の形をしたものを探す。値は伏せ、ハッシュと位置だけを記録する。(b) 鍵：**ラボに同梱した廃止済みの模擬鍵**で署名したトークンを1回送る |
| 期待する証拠 | (a) 種類、ファイル、位置、伏せた値のハッシュ。(b) 受け入れられたかどうか |
| 修正の方法 | 秘密情報をクライアントに置かない。鍵をローテーションし、古い鍵を無効にする |
| 合格の基準 | (a) 正解の分かっている20ファイルで、誤検知の率が 5% 以下。(b) 誤検知0 |

### S5：クラウドの権限（T1580、T1069.003、T1098.003、T1651）

| 項目 | 内容 |
|---|---|
| 模擬データ | 所有者が提出した IAM ポリシーの JSON（模擬）。クラウドの API には接続しない |
| 安全な検証 | **ネットワークを使わずに**ポリシーを解析する。たとえば `ssm:SendCommand` を `*` に、`iam:PassRole` と `ec2:RunInstances` の組み合わせ、認証情報の追加の権限など |
| 期待する証拠 | 該当した文、その権限で何ができるか、根拠となる ATT&CK の ID |
| 修正の方法 | 最小権限にする。条件（タグ、リソース）を付けて絞る |
| 合格の基準 | 正解付きの模擬ポリシー30件で、適合率と再現率の両方が 0.9 以上 |

## 5. ARTEX と Abliteration AI の役割を分ける

| 測るもの | 中身 | 評価の方法 |
|---|---|---|
| **検査を選ぶ力**（モデル） | 観測した表面（エンドポイント、Content-Type、SAML のメタデータの有無など）から、どの検査が必要かを選ぶ | 正解付きの選択の課題（S1〜S5 と既存の検査、各40条件）で、適合率、再現率、範囲外の提案の数を測る。台本どおりに答える代わりの仕組み → 模擬 LLM → 実モデル（承認と費用の上限が必要）の順に進める |
| **脆弱性を実証する力**（Worker と判定器） | 決められた要求を送り、証拠から判定する。モデルは関わらない | 検査ごとに「脆弱な設定」と「修正済みの設定」の組を作り、検出率と誤検知の率を測る。モデルの出来に左右されない |

この2つを掛け合わせた「全体の発見力」は、両方を測ってから報告します。片方だけを測って、全体の発見力として報告することはしません。
