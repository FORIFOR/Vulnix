# HTTP 200認証エラーの独立ラボ

所有者仕様で認証必須とされたルートでも、HTTP 200のJSONが認証エラーだけなら保護データの取得は確認できない。`tests/fixtures/auth_response_lab.py` は診断器を参照しない独立したループバック対象で、正解は `tests/fixtures/auth_response_truth.json` に分離した。

| 条件 | 正解 | 修正前 | 修正後 |
| --- | --- | --- | --- |
| 保護データを含む200 | 検出 | detected | detected |
| 認証エラーだけの200 | 非検出 | detected | candidate |
| 認証エラーと固定コードだけの200 | 非検出 | detected | candidate |
| Content-Lengthなしの認証エラー200 | 非検出 | detected | candidate |
| 認証エラーと保護データを含む200 | 検出 | detected | detected |
| 認証エラーの文字列内に保護データを含む200 | 検出 | detected | detected |

修正前はTP 3・FP 3・FN 0・TN 0、修正後はTP 3・FP 0・FN 0・TN 3。各条件で対象GETは1回。修正前の誤検知は先行テストで再現してから修正した。本文全体の受信を確認したうえで、認証エラーだけのJSONか、認証エラーと固定コードだけのJSONで、文字列が限定した認証拒否文言と完全一致する場合に限って `candidate` へ下げる。`Content-Length` がある場合は本文バイト数と一致させ、ない場合はHTTP読み取りが上限4KBより短くEOFに達したことを条件にする。本文が途中で切れた場合、余分なデータを含む場合、形式が不明な場合はこの例外を適用しない。一般的な200 JSON認証拒否をすべて網羅したわけではない。

診断器単体の評価に加え、同じ6条件を既存Gatewayと隔離Workerの読み取り専用ルートでも通した。Gateway呼出し6回、Worker起動6回、対象GET6回で、判定はTP3・FP0・FN0・TN3のままだった。これは模擬対象の所有権・範囲条件であり、公開βの実DNSと実サイト実行を証明しない。

この6条件は既存の14条件の承認済みAbliteration AI評価入力には追加しない。ARTEXによる検査選択や実サイトでの精度は、この小さなラボからは判断できない。実サイトへの通信、有料API呼び出し、L2実行は行っていない。
