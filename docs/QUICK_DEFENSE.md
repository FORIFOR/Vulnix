# 個人開発者向けのかんたんセキュリティ検証

最優先は、個人開発者が自分のサービスについて、公開された攻撃に関係する防御を短時間で確認し、修正後に確かめ直せること。評価には、検証できる防御項目、未確認の根拠、開始までの操作数を使う。

## 一次資料

- A. [CrowdStrike — 韓国の金融機関を対象としたARTEX関連活動](https://www.crowdstrike.com/en-us/blog/unknown-threat-actor-uses-artex-to-target-south-korean-finance/)
- B. [CrowdStrike — VAPOR PANDA](https://www.crowdstrike.com/en-us/blog/vapor-panda-uses-artex-to-scale-global-campaign/)
- C. [CrowdStrike — エージェント型AIを使った4件のキャンペーン](https://www.crowdstrike.com/en-us/blog/crowdstrike-uncovers-new-agentic-ai-campaigns/)
- D. [Anthropic — Claude Codeを悪用した諜報活動](https://www.anthropic.com/news/disrupting-AI-espionage)

AはARTEX利用と侵害を報告するが、個々の被害環境の侵入経路は確定できない。Aに関する管理面・公開面の確認は、この報告から導く防御上の確認事項として扱う。ARTEXプランナーの接続はVulnixの実行経路の確認であり、対象サービスの耐性については個別の証拠が必要になる。

## 現在の自動検証範囲

分母は上表の11行（公式報告から整理した防御項目10行と公開CVE 1行、対象外の「多段階の侵入」行を除外）。フォルダ選択だけで解析できる項目は3/11（27%）で、メタデータ設定、S3公開防止、公開CVEの各行に部分対応する。公式報告の防御項目に限ると2/10（20%）。実稼働環境の全要件を確認できる行は0件。HTML出力の検査は追加の防御検査で、公式報告がその攻撃経路を確認したという扱いには含めない。

| 自動検証 | 対応する防御・根拠 | 未確認時の追加確認 |
| --- | --- | --- |
| CloudFormation JSONのEC2起動テンプレート | Bのクラウド資格情報対策。メタデータ停止・トークン必須・明示的な旧方式の許可を区別する | 起動したインスタンスを選び、メタデータの実効設定と付与ロールを照合する |
| CloudFormation JSONのS3公開ブロック | A/B/C/Dのデータ公開・持ち出し対策。4つのブロック設定を照合する | バケットと組織・アカウント側の公開設定を照合する |
| JavaScript/TypeScriptのHTML出力 | 同じブロック内でそれ以前に定義したconstなどをたどり、要求由来の式とHTML・テキスト出力を区別する | 関数呼び出し、条件分岐、別ファイル、ライブラリ、稼働時の入力経路は別途確認する |
| 公開CVE | Dockerfileの明示的な公式ApacheタグとCPE付きCycloneDXをNVDに照合。同じインベントリ内のAND/OR条件を調べ、異なるインベントリを結合しない | パッチやバックポート、稼働中の版をベンダー勧告と照合する。否定付き・複雑なCPEは未対応 |
| npm依存関係 | npm lockfile v2/v3を認識し、HTTP取得元とOSVに明記された固定影響版をチェック | OSVの範囲だけの記録、npm以外の版照合、レジストリの真正性は未確認 |

[S3設定仕様](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-s3-bucket-publicaccessblockconfiguration.html) ／ [EC2設定仕様](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-ec2-launchtemplate-metadataoptions.html) ／ [NVDの複合条件](https://nvd.nist.gov/vuln/Vulnerability-Detail-Pages) ／ [OSV仕様](https://ossf.github.io/osv-schema/)

## 使い方と上限

ダッシュボードでローカル診断を開き、フォルダを選んで開始する。修正後は同じフォルダを選び直す。証拠JSONの作成は不要。依存関係情報や言語・フレームワークはソース拡張子と既知のマニフェストから推定する。npm、Python、Goなどの既知のロックファイル名を識別する。認証・認可・DB・XMLなどに関連する名前のソースを優先して読み、扱える検査がなければ未確認とする。SAML、XML、認可の実効性は対象ライブラリの設定や権限外入力を拒否するテストを照合する。

入力はブラウザ内のWorkerで処理する。列挙12,000件、読み取り180件、単体256 KiB、合計6 MiB、実行8秒が上限。隠しファイル、資格情報の名前、依存・生成ディレクトリは除外し、結果にコード断片、ファイルパス、設定値やURLの生値を出さない。OSV・NVDは2 MB以下のJSONを手動で選ぶ。ローカル結果、模擬データ、所有確認済みのサイトと隔離ラボは別の表示と導線を使う。

## OSSの採否

- TypeScriptの構文木を採用。既存依存でJS/TSを解析でき、対象コードの実行や別途インストールを必要としない。今回の限定ルールによる判定であり、プロジェクト全体の型・データフロー解析は未対応。[コンパイラAPI](https://github.com/Microsoft/TypeScript/wiki/Using-the-Compiler-API)
- Semgrep CEはより広いルールに対応する候補。今回のブラウザだけの導線では、別途エンジンとルールの配布・保守が必要なため採用を保留した。精度の直接比較は未実施。[Semgrep CE](https://semgrep.dev/products/community-edition/)
- OSV-Scannerのオフライン方式を調査。多形式のロックファイルを扱えるが、端末バイナリとエコシステム別DBの準備が必要なので組み込まなかった。今回はOSV形式の明示版一覧を手動入力に採用した。[オフライン方式](https://google.github.io/osv-scanner/usage/offline-mode/) ／ [ソーススキャン](https://google.github.io/osv-scanner/usage/scan-source)

## 別の模擬プロジェクトによる受入評価

前回の固定証拠JSONを使わず、別の合成フォルダを実際のブラウザから選んだ。既存の新規ユーザー作成フローを使い、同じ利用者で修正・再選択・再検証を行った。判定の正解は用意したコード・設定・カタログで定義した。独立レビュアーおよび未知の実務プロジェクトでの評価は未実施。

| 分類 | 判定数 | 検出 | 誤検出 | 見逃し | 未確認 |
| --- | ---: | ---: | ---: | ---: | ---: |
| ARTEX | 3 | 1 | 0 | 0 | 1 |
| CVE | 7 | 1 | 0 | 0 | 6 |
| Claude Code | 5 | 1 | 0 | 0 | 2 |

検出は期待された「対策が必要」と一致した件数。見逃しは明示的に対策が必要という正解を取り逃した件数。カタログの構成条件だけが一致し、稼働状態が不明な例の正解は未確認とした。件数は表の指定項目のみで、情報不足時の一般的な案内行は除外した。

開始まで3操作（入口・フォルダ選択・開始）、修正後の再検証は2操作。3分類の検証を同時に実行し、3構成で0.224 / 0.210 / 0.212秒（フォルダ選択の自動操作から結果まで）。分類単独の時間は測定していない。合成ファイル生成は0.001秒で、利用者による証拠の事前準備は0操作。実際の利用者が対象を探す時間は未計測。外部通信、ファイル送信は各0件。
