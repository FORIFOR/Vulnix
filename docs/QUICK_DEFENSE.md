# 個人開発者向けのかんたんセキュリティ検証

最優先は、個人開発者が自分のサービスについて、公開された攻撃に関係する防御を短時間で確認し、修正後に確かめ直せること。評価には、検証できる防御項目、未確認の根拠、開始までの操作数を使う。

## 現在の自動検証範囲

分母は上表の11行（公式報告をもとに整理した10行と公開CVE 1行。多段階侵入の再現は対象外）。フォルダ解析で **10/11行（91%）に部分対応**する。公開CVEを除いた公式報告由来の要件は **9/10行（90%）**。行に含まれる一部の静的設定を評価した割合であり、実稼働で行全体を確認した項目は0件。

次の照合はいずれもローカルの資料に対して行う。

- Bで報告されたSAML・XML・クラウド経路。Node-SAMLとPassport-SAMLの直書きオプション、libxmljsの実体・DTD設定、EC2メタデータ設定を読む。SAMLの署名必須を明示していても導入版、IdP、署名拒否テストを確認する。XMLの引数が動的または対応外の場合はライブラリの実効フラグを確認する。
- 公開面・通信・権限・データ。CloudFormationの管理ポート、APIステージの既定制限、S3公開防止、Kubernetes JSONの広すぎる外向き規則とRBACワイルドカードを確認する。一般的な防御への変換であり、報告された被害環境にこの構成が存在したという記録ではない。利用中のルート設定、RBACの付与先と合成、組織側のストレージ設定を確認する。
- 資格情報と成果物。秘密鍵形式とGitleaksの任意レポートを候補として表示し、Dockerfileの最終ステージでの明示rootを検出する。値は表示しない。MFA、認可、失効、イメージ署名、稼働時の上書きは、IDプロバイダー設定、別主体拒否テスト、失効履歴、署名検証結果、実効Pod設定を確認する。
- 公開CVE。NVDの対応するCPE条件、OSVの明示版と範囲に対応する。npmは整合性欄を持つHTTPSロック記録のSemVer、PyPIはマーカーなしの正確なrequirementsピンとPEP 440、Goは置換や除外のないgo.modの同一モジュールパスとSemVerを使う。Goの実際の解決版は別途確認する。Gitコミット範囲、PEP 440のローカル版、未対応ロック、複雑なCPE、バックポートと到達性は未確認。
- 追加検査として限定的なJS/TSの同一ブロックのHTMLデータフローを読む。アプリ全体の到達性と安全性は確認しない。

Claude Codeでは共有プロジェクト設定だけを読み、運用者の信頼状態や上位設定は未確認とする。対象固有の実際のツール一覧・書き込み操作の承認ルール・拒否履歴も確認する。メールやVPN、ディレクトリサービスでは管理面のMFA、署名鍵の更新記録、委任の一覧を確認する。メール・VPN・ディレクトリサービスの行には専用の自動照合がない。

## 使い方と上限

ダッシュボードでローカル診断を開き、フォルダを選んで開始する。修正後は同じフォルダを選び直す。証拠JSONの作成は不要。依存関係情報や言語・フレームワークはソース拡張子と既知のマニフェストから推定する。npm、Python、Goなどの既知のロックファイル名を識別する。認証・認可・DB・XMLなどに関連する名前のソースを優先して読み、扱える検査がなければ未確認とする。SAML、XML、認可の実効性は対象ライブラリの設定や権限外入力を拒否するテストを照合する。

入力はブラウザ内のWorkerで処理する。選択は12,000件まで。対象を最大180件・12 MiBのバッチに分け、選択したフォルダを順に検査する。相対パスの重複を除き、ソース単体256 KiB、対象依存関係資料単体4 MiB、処理時間30秒（Worker強制停止は35秒）を上限とする。中断時は直近の進捗と未処理ファイルの先頭10件を表示する。完了時は読取上限・読取失敗・未対応・時間切れの件数と、該当ファイルを最大100件表示する。ソースのデータフローは単一ファイル内を対象とする。

共有の `.claude/settings.json` とCI定義を例外とし、隠しファイル、資格情報の名前、依存・生成ディレクトリは除外する。結果には相対パスと特定できた行番号を表示する。コード断片、資格情報、URL、生の設定値を出さない。OSV・NVDは2 MB以下のJSONも手動で取り込める。取得日時は資料にある場合に表示し、手元での読込日時を区別する。ローカル結果、模擬データ、所有確認済みのサイトと隔離ラボは別の表示と導線を使う。

## 実務プロジェクト向け更新

「NVD・OSVの公式データを取得」を押すと、OSVの npm・PyPI・Go の `all.zip` と、NVDの2002年版（それ以前の勧告を含む）から今年までの年次フィードを順に取得する。選択したフォルダ、パッケージ名、版、CPE、資格情報は、取得リクエストにも照合リクエストにも使わない。公式取得には既存のログイン・同一オリジン検査と固定の提供元を使う。通常の診断はブラウザ内に保存された公開カタログを再利用し、外部通信は手動操作のときだけ行う。

アーカイブは提供元・年単位に分ける。OSVはZIPと各メンバーを、NVDは公式メタデータの展開サイズとSHA-256を検証する。ブラウザのWorkerで小さな単位に分けてIndexedDBへ書き、パッケージ名や製品のCPEで索引を引く。書き込みとストリームの完了を確認してから、その範囲の索引を切り替える。取得失敗、切断、端末の保存領域不足では、正常な旧索引を維持する。撤回・却下の勧告は照合から外す。同じCVEに紐づく複数の依存関係を同じ結果に表示する。

最初の取得は大容量。更新は範囲ごとに最大8分のサーバー処理時間、全体で最大25分のブラウザ取得時間を設ける。保存済み・未収録の範囲、取得日時、提供元日時、収録件数と索引件数を画面で確認できる。索引対象の候補が16 MiBまたは12,000レコードに達した場合や時間切れは、未確認の範囲が残ることを表示する。NVDの未評価レコード、対応外のCPE・版範囲、OSVのCVE IDを持たない勧告は、脆弱性が存在しない根拠にしない。任意の小さなJSONの取り込みは従来どおり2 MiBまで。

KubernetesのJSON/YAML、TerraformのJSON構文（`.tf.json`）、Dockerfile、GitHub ActionsのYAMLに対応する。YAMLはcoreスキーマを使い、重複キー、カスタムタグ、エイリアスを拒否する。Terraform HCLの評価、変数展開、YAMLでのテンプレート生成、デプロイ、コンテナ実行は扱わない。GitHub Actionsでは全書き込み権限やコミット未固定の外部アクション、Dockerfileでは最終ステージの実行ユーザーを確認する。実効権限や環境側の上書きは別途確認する。

結果は100件ずつ表示し、保持する所見を最大5,000件に制限する。表示・保持上限に達しても後続ファイルの解析を続ける。結果の集計は保持できた所見に基づき、保持できなかった件数は別途表示する。

先行評価では公式勧告を使用し、Apache HTTP Server 2.4.49と2.4.51、lodash 4.17.20と4.17.21を区別できることを確認した。同じ公式OSV勧告を使用したオフラインのOSV-Scannerも、lodashの影響版だけを報告した。NVDの複合条件は、CVE-2014-0160のファームウェアと版番号のない機器を同じCycloneDX資料で示したときに一致し、機器が欠落または別資料の場合は条件未確認になった。いずれもカタログと資料の照合結果であり、稼働状況や配布元修正の確認は別途必要になる。

### フォルダ診断からの追加確認

検証結果の「実行時の防御確認へ」から、項目の合格条件と、読み取り専用で確認する設定を参照できる。既に使っているテストランナーのJUnit出力を直接選択する。Vitestでは `--reporter=junit`、pytestでは `--junitxml`、Nodeのテストランナーでは `--test-reporter=junit` が利用できる。対象プロジェクトで実行が承認されているテストだけを選び、ネットワークを遮断した隔離環境と合成データで実行する。

- 設定と依存関係から検証項目を選び、該当しそうな既存テストの位置と許可側・拒否側の確認候補を表示する。対応候補はコード上の条件の手掛かりであり、実際にその条件が成立したことの証拠には使わない。候補が出なかった項目は未確認のまま残る。
- **利用者確認（テスト結果）**は、JUnitの成功ケースと対象コミット、配備版、実行環境、報告書のSHA-256を対応付けた記録。JUnitに `vulnix.commit`、`vulnix.deployment`、`vulnix.environment` のプロパティがある場合は入力と一致する必要がある。出所と合格条件の充足を独立に検証できないため、自動の動作確認済みにはならない。失敗・エラー・スキップは選べない。
- 「Vulnix自身の隔離・実行制御を確認する」から、既存の設定画面へ移動できる。ここでの結果は診断側の制御に限る。
- **設定確認済み**は、利用者が許可範囲内の管理画面などで対象設定を読み取った記録。対象の防御動作には別の確認が必要。
- **対策が必要**は、実際に観測した不適合の根拠がある場合に記録する。テスト基盤のエラーや情報不足の場合は**未確認**にする。
- **根拠付き対象外**は、運用構成などで対象技術を使っていない根拠を確認できた場合に限る。

テスト名、標準出力、失敗本文は画面に取り出さず、ファイルや記録を送信しない。記録はブラウザの現在の診断に限り、再検証や対象フォルダの変更で消える。設定・理由欄へ秘密値や個人情報を入力しない。

### レビュー済みMFAテストの隔離ランナー

起動済みのVulnix用Limaゲストで、`python3 -m aegis.local_defense <対象フォルダ>` を実行すると計画が出る。固定の既存テストとコードのSHA-256、レビュー版、合格条件、実行制限を確認し、同じコマンドに `--approve <計画SHA-256>` を付けると実行する。対象はレビューしたVulnixのMFAテスト1件。必要な4ファイルを再照合し、ワーカーから書き込めないコピーを渡す。Linuxの名前空間、cgroup、seccompを確認できない場合は未確認になる。テストが使うのは合成アカウントだけ。ランナーはオペレータの環境変数や認証情報を引き継がない。

ランナーは既存テストに加えて、合成アカウントで第二要素あり・なし・不正の3条件を実行する。正しい第二要素ではセッションが解決でき、残りの2条件はMFAで拒否され、既存テストも成功した場合に合格とする。条件に反する動作の観測は不合格、観測欠落や隔離・テスト基盤の異常は未確認になる。

JSON結果には実行ID、条件ごとの観測と既存テストの結果、計画と観測結果のハッシュ、レビュー済みのファイル群、隔離環境を記録する。ハッシュは内容確認に使う。`--junit` を追加すると、フォルダ診断から取り込めるJUnitを出力する。ブラウザから見ると利用者が渡したファイルなので、「利用者確認（テスト結果）」として扱う。

### レビュー済みNode.jsバンドルとブラウザからの実行

Node.jsプロファイルはLinux arm64向け。対象は登録済みの24Call OEMのレビュー版と合成フィクスチャ。Node.js v22.23.5の公式配布アーカイブ・実行ファイル、二つのnpmマニフェスト、ソースのファイルマニフェスト、テスト選択、依存関係ツリーのSHA-256は [aegis/local_defense_node.py](../aegis/local_defense_node.py) に記録する。準備したバンドルは以下の構成で、元プロジェクトやリポジトリと別の0700ディレクトリに保管する。

| バンドルの相対位置 | 準備 |
| --- | --- |
| `node-v22.23.5-linux-arm64/bin/node` | 公式のLinux arm64アーカイブと同じリリースのSHA-256表を取得し、表とプロファイル双方に照合して展開する。展開後のバイナリも照合する。 |
| `dependencies/package.json` と `dependencies/package-lock.json` | レビュー版から写し、プロファイルに照合する。ロック内が公開npmレジストリへのHTTPS参照に限られることを確認する。 |
| `dependencies/node_modules` | 分離した作業ディレクトリで、上記のNode.jsをPATHの先頭に置き、空のユーザー・グローバルnpm設定で `npm ci --ignore-scripts --no-audit --no-fund` を実行する。準備時だけ公開レジストリへ接続する。以後は保存済みツリーを使う。 |
| `reviewed/` と `selection.json` | 管理者が保管したレビュー済みのソース閉包、補助フィクスチャ、固定の選択定義をそのまま転送する。ファイルもマニフェストもプロファイルに照合する。再レビューなしで版やテスト選択を更新しない。 |

CLIでは `python3 -m aegis.local_defense --node <バンドル>` で計画を確認し、`--approve <計画SHA-256>` で実行する。Node.jsとPythonは同じWorker・カーネル隔離・撤収手順を使う。保存済みバンドルにレビュー済み `defense-observer.test.ts` を追加すると、固定の10件とは別のWorker実行で、認証・認可・テナント選択・Webhook署名・AI操作ポリシーそれぞれの許可・拒否を観測する。管理側が条件ごとに判定する。観測ファイルを用意していないバンドルではテストの集計を表示する。

固定の受入プロファイルは `--local-defense-python-root <レビュー済みVulnixのフォルダ>` と `--local-defense-node-bundle <バンドル>` で既定の組織に登録する。フォルダを選び「実行計画を見る」を開くと、ブラウザ内で対象のSHA-256を照合する。依頼と実行で送信するのはプロファイルの識別子とハッシュ。独立した承認責任者が承認し、依頼者が開始する。承認は10分で失効し、再検証には新しい承認が必要。緊急停止と実行の中断は隔離Workerを停止する。

自動結果はサーバーが開始・監視した固定実行からだけ作成する。サーバー側の証跡には依頼、承認、計画、対象、隔離の確認結果、観測、判定の対応を記録し、監査ログに証跡ハッシュを残す。ブラウザに結果の取込みAPIはない。JUnitの手動取り込みは引き続き利用者確認。再起動後に実行権限や自動判定を引き継がない。

### 自分のPython・Node.jsプロジェクトを登録する

静的診断とCVE診断はフォルダ選択だけで利用できる。動作確認を追加する場合は、ローカルLinuxの運用者が合成データ専用のバンドルと承認担当者を準備する。

1. 非公開の保管ディレクトリを0700で作る。対象の版から、試験に必要なソースとローカル依存だけを `<bundle>/source/` に置く。設定の秘密値、本番データ、環境変数、ネイティブ拡張、`node_modules` は入れない。
2. 合成入力で実際の処理を呼び、許可を `true`、明示拒否を `false`、判断不能を `null` として返す観測アダプターを用意する。Pythonは `check.py` の `observe(name, inputs)`、Node.jsは `check.cjs` の `exports.observe` に固定する。アダプターをプロジェクトの診断用コピーにも含める。ファイル、呼ぶ処理、許可側・拒否側で結果を変える条件をレビューする。
3. `<bundle>/profile.json` にバージョン、識別子、言語、表示名、レビュー版、SHA-256付きのファイル一覧、両側の合成入力を書く。対応カテゴリは `authentication`、`authorization`、`tenant-selection`、`webhook-signature`、`ai-policy`、`mfa`。観測の欠落は未確認。次は構造を示す例で、ファイルのSHA-256を実値に置き換える。

```json
{
  "version": 1,
  "id": "my-project",
  "language": "python",
  "title": "組織メンバーの認可",
  "revision": "reviewed-commit",
  "files": {"check.py": "<SHA-256>"},
  "checks": {"authorization": {"allow": {"role": "member"}, "deny": {"role": "viewer"}}}
}
```

4. 運用者が管理する0600のレジストリをバンドルの親ディレクトリに置く。レジストリの各要素には組織ID、バンドルのディレクトリ名、レビュー済み `profile.json` のSHA-256、Node.jsランタイムの固定情報を記録する。Pythonでは `"node": null` を指定する。Node.jsでは `"node": {"path": "<絶対パス>", "sha256": "<SHA-256>"}` を指定する。Node.jsランタイムは管理者が公式配布元から取得・照合し、対象Linuxで動くものを使う。

```json
[{"org": "<組織ID>", "bundle": "my-project", "sha256": "<profile.jsonのSHA-256>", "node": null}]
```

5. コントロールプレーンを `--local-defense-registry <registry.json>` 付きで起動する。対象組織に切り替え、フォルダを選び、計画を依頼する。承認後に実行し、項目ごとの観測と、失敗・未確認時の再検証案内を確認する。

この形式は小さなオフライン検査向け。Python標準ライブラリ、Node.js組み込みモジュール、レビューしたローカルソース閉包を使う。外部依存インストール、ブラウザからの実行コマンド入力、実サービス通信、未レビューのコードは対象外。ライブラリやプロトコルの観測アダプターが用意できない項目は未確認にする。実DB分離や実効IAMなど、対象環境でしか観測できない項目には該当する環境の根拠が必要。

### リリースとロールバック

統合は #127 → #128 → #129 の順。配備を承認する前に最終SHAのCI、カーネル隔離、テナントごとの承認を確認し、ローカル受入とSTG受入の証跡を分けて記録する。リリースノートに含める変更は組織別のレビュー済みプロファイル、項目別の許可・拒否観測、修正案内。静的診断とCVE照合は管理者のバンドル準備を必要としない。動作確認には保管バンドル、Linux隔離、別人承認が必要。

切り戻す場合は既存の緊急停止を使い、隔離資源の回収を確認してから、起動時の `--local-defense-registry` と必要に応じて固定プロファイルのフラグを外す。前のアプリ版と同じデータディレクトリを使う。レジストリとバンドルは退避し、監査ログを保持する。再有効化の際は対象版とファイルの照合からやり直して新しい承認を取る。

### 許可済みSTGでの受入条件

| 許可範囲 | 具体的な受入確認 |
| --- | --- |
| 対象の所有者が、STGのホスト・配備版・時間帯・許可経路を明示する | テスト用の配備版と実効設定を対応付け、承認した経路だけを対象にする |
| 合成データを持つ二つのテスト組織と、各テストアカウントの操作が許可される | 許可された役割の操作と拒否される操作、認証・MFA・Webhook署名、組織分離を確認する |
| IdP、IAM、ネットワーク、ストレージ、コンテナ、エージェントの閲覧権限が付与される | 対象に適用されたSSO、MFA、IAM、出口、データ権限、実行UID、ツール許可を読み取り専用で確認する |
| SAML・XMLを使う経路と、既存の防御テストの使用が明示される | 各ライブラリの拒否動作と正規ケースを、対象の隔離した試験環境で確認する |

STGの確認は環境所有者の許可後に限る。既存の所有確認・承認に従い、受入中は設定変更やデプロイを行わない。

### 適用条件と実行時の確認

ローカル画面で「設定・コードを確認」と表示するのは、対象資料から根拠を確認できた箇所。動作の確認には、使用中のライブラリ、配備設定、権限などに対応する既存テストや隔離環境での観測が必要になる。確認を実行できない項目は未確認。機能を使用しない場合は、運用構成や依存関係一覧などの根拠を記録して対象外とする。

| 防御 | 適用条件と静的証拠 | 動作確認の合格条件 | 実務対象での状態 |
| --- | --- | --- | --- |
| 公開サービス・管理面 | 管理経路やポートを公開する構成。デプロイ定義と公開ルート一覧 | 架空の管理者・一般利用者がいる隔離環境で、許可された管理者の操作だけが成功する | 配備先の入口は未確認 |
| SAML署名 | SAMLを使用し、信頼するIdPの署名を要求する構成 | 既存SSO試験で、テスト用IdPの正規署名は受理し、署名なし・不正署名・信頼外の鍵は拒否する | 対象のSAML実行時は未確認。OIDCの試験はこの項目の証拠に含めない |
| XML外部資源 | XMLを解析する機能。明示したライブラリとパーサーのオプション | 隔離環境のパーサー試験で、外部資源を解決するコールバックの呼出が0回であることを確認する | 対象のXML実行時は未確認 |
| 実行権限・クラウド管理面 | クラウドのロール、メタデータ、管理面を運用する | 最小権限ロールの操作だけが成功し、許可外の権限を使えない | 実効IAM・メタデータ・管理面は配備環境の設定ビューが必要 |
| 認証・認可・MFAと資格情報 | ログイン、役割、組織、Webhookを扱う。適用している認証方針と値を伏せた棚卸しを確認 | 有効な認証・権限で操作でき、無効な認証・権限では操作を拒否する | Vulnixの内部MFAと、24Callの認証・認可・Webhook署名を隔離で観測。配備版の実効MFA・失効方針は未確認 |
| プロキシ・レート・外向き通信 | プロキシ、API制限、出口方針を運用する | 許可した接続だけが通り、規定の要求上限を超えない | Workerの遮断はVulnix自身の制御。対象環境はルート別の実効設定と監査記録が必要 |
| エージェント操作 | AIツールが読み取りや状態変更を行う | 許可操作が成功し、許可外操作を実行しない | 24Callの操作ポリシーの許可・拒否を隔離で観測。配備環境の許可一覧とモデル構成は未確認 |
| データ分離・持ち出し | 複数組織のデータ、ストレージ、外向き連携を扱う | 所属組織への正規操作だけが成功し、所属外操作は状態を変えない | 24Callの組織選択を合成DBアダプターで観測。実DBの行権限、ストレージ、実効出口制御は未確認 |
| コンテナ・成果物・永続化 | コンテナまたはCIでビルドする。ユーザー、署名、書込範囲の明示 | 対象を実際に起動する検証環境で非root UIDと書込制限を観測する | Dockerfileの静的所見まで。24Callの起動やデプロイは未実施 |
| メール・VPN・ディレクトリ | 運用構成で利用が判明した場合 | 使用中の製品に応じた既存の拒否試験と実効設定を確認する | 製品別検証は未対応。利用しない根拠が揃う場合に対象外 |
| 公開CVE | 固定依存関係や製品CPEと、カタログの構成・影響条件 | 影響版では勧告に一致し、修正版の資料では候補が解消する。配備済み版は別途確認する | 固定依存関係とNVDの対応CPEを照合できる。実行環境の版・到達性は未確認 |
