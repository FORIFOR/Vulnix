# AI アドバイザー 次の設計案: 修正案のカタログ ID 化と、自由文章の非実行化

状態: 提案（未実装）。前提は、評価の仕組み（`docs/advisor_eval_report.md`）による実測です。

## 1. 今の到達点と、残っている問題

| 部分 | 今の形 | 保証 |
|---|---|---|
| 次の確認項目 | `operation` の id と `purpose` の id だけ | 構造で保証（自由文章はない） |
| 修正案の種類 | `fix` の id（規則ごと、判定ごとに許可） | 構造で保証 |
| 修正案の説明（`detail`） | 自由文章 | 最善の努力。危険な指示の拒否率は **49.3%**（holdout）で、高めの見積もり |
| リスクの説明（`risk_explanation`） | 自由文章 | 漏れと誇張の検査だけ |
| 状況に合うかどうか | 判定と規則で絞るだけ | 状況に合わない提案の受理率は **71.3%** |

文章の検査に禁止語を足していくやり方は、言い換えのすり抜けと、正当な文の誤った拒否を繰り返しました（独立レビューで3回）。次の段階では、文章で判定する範囲をさらに減らし、残る文章は実行に使わないことを、仕組みとして保証します。

## 2. 修正案のカタログ ID 化（`detail` をなくす）

1. **修正案は id と、列挙された引数だけにする**: `fix` ごとに、カタログが引数の型と、取りうる値を持ちます。
   - 例: `set_hsts` は `max_age` を `6m`、`1y`、`2y` から選び、`include_subdomains` は真偽値。
   - 例: `restrict_cors_allowlist` は `scope` を `exact_origins`、`same_site` から選ぶ。
   - モデルは id と値を選ぶだけです。
2. **表示する文はコードが作る**: 画面と報告の文は、カタログのひな形に引数を入れて作ります（日本語と英語）。モデルの言葉は使いません。
3. **自由な補足は、別の欄に分ける**: 必要な場合だけ、`note` を1つ持てるようにします。扱いは 3 で述べる「信頼しない文章」です。ここが空でも、助言は成り立ちます。
4. **効果**: 危険な指示を、修正案として表す方法がなくなります。今の 49.3% の弱点がそのまま消え、評価は構造の検査に移ります。
5. **カタログの見直しを人が行う**: 新しい id と引数を足すのは、コードの変更とレビューを通してだけにします。モデルの出力から、カタログが増えることはありません。

## 3. 自由文章の非実行化（説明文と `note`）

1. **専用の型で包む**: `risk_explanation` と `note` は `UntrustedText` で包みます。文字列としては取り出せず、表示用に変換する口だけを持たせます。
2. **実行への経路を、テストで塞ぐ**: `UntrustedText` が次の場所に届かないことを、構文木の検査と実行時の確認で保証します。
   - Gateway、ProposalRouter、Worker の argv と環境変数
   - 別のモデルへのプロンプト
   - 監査ログのキー
3. **表示は、ただの文字として行う**: UI では、React の通常の文字表示だけを使います。Markdown、リンク、HTML として解釈しません。
   - 「AI の文章（未検証）」と明示し、コードが作った説明とは見た目を分けます。
4. **出力と保存の扱い**:
   - Remotion への出力と、公開用の出力からは、既定で外します。
   - 状態ファイルに保存するときも、コードが作った文とは別の欄にします。
5. **検査は、表示前の安全確認に限る**:
   - 漏れ（URL、IP、資格情報）と誇張の検査は残します。
   - 危険な言い回しの検査は、実行の安全とは関係のない、表示の品質の問題として扱います。

## 4. 状況に合わない提案（71.3%）を減らす

1. **モデルに、所見の評価を列挙値で答えさせる**: `assessment` を `likely_true_positive`、`likely_false_positive`、`needs_evidence` から選ばせます。
2. **評価と、ほかの答えの整合をコードで検査する**:
   - `confirm_intended_exposure` を使えるのは `likely_false_positive` のときだけ。
   - 本来の修正（`require_authentication` など）を使えるのは、`likely_true_positive` のときだけ。
   - `needs_evidence` のときは、証拠を集める確認（`collect_evidence`）か、人による見直しだけ。
   - `claim_level` との矛盾（`observed` と `likely_false_positive` の組み合わせなど）も拒否する。
3. **限界**: 誤検知かどうかの判断そのものは、モデルに任されたままです。保証できるのは、答えの内部の整合だけです。評価データで、`assessment` の正解率を新しい指標として測ります。

## 5. 実行の側（変えないこと）

- 次の確認項目は、提案のままです。
- 実行するには、人が `operation` の id を選ぶ必要があります。そのうえで、コードが固定の対応表で Gateway のツールと引数に変換し、既存のゲート（所有確認、範囲の承認、L2 の承認、緊急停止）を通します。
- 対応表の値は、モデルの出力からは決まりません。URL や対象も、確認済みの資産から取ります。

## 6. 評価の進め方

1. **人によるラベルのレビュー**: 今のラベルは、検証器を作った本人が書いたものです。
2. **独立した holdout**: 別の書き手による例文を用意します。規則を知らない人に書いてもらいます。
3. **新しい指標**:
   - `assessment` の正解率
   - 引数つきの修正案の妥当性
   - `UntrustedText` が漏れ出た件数（0 件をゲートにする）
4. **実モデルでの評価**: 実際の Abliteration AI での評価は、API キー、課金、データの扱いについて利用者が判断してから、別の段階として行います。その結果は、模擬サーバーの結果とは分けて報告します。

## 7. 実装の順序（案）

1. カタログに、引数の定義と表示のひな形を加える。`detail` を廃止し、`note` を `UntrustedText` にする。
2. `UntrustedText` の型と、経路を塞ぐテスト（構文木と実行時）。
3. `assessment` と整合の検査。評価データにラベルを追加する。
4. UI の表示（未検証の文章を分けて表示する）。画面で見た目を確かめる。
5. 評価レポートの更新と、独立レビュー。
