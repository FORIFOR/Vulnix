## 2. ラベル付けの基準（事前に固定）

1. **`l2_idor`**：アカウント資源へのリンクが観測され、所有者の意図が本人限定である場合に選びます（構造化項目でもメモでもよく、メモが「未指定」や古い「公開」を上書きします）。重大扱いです。
2. **`l1_apache_mod_status`**：Apacheである（メモで背後のApacheが分かる場合を含む）、かつ同意がある場合に選びます。ただし、所有者が意図的な公開とリスク受容を明言した場合は除きます。無効化や制限の確認は必要として扱います。
3. **`l1_http_probe`（1回だけの再取得）**：報告対象になる観測の証拠が揺れている場合に選びます。所有者のメモが不安定さや観測との矛盾を示し、観測が1回しかない場合も同様です。また、同名のセッションCookieの属性が食い違う場合にも選びます。

## 5. AIの起動条件（改善がない場合の設計）

`ai_invocation_gate`：B2で判断し、**メモがある、または構造化要件が「未指定」の条件だけ**をモデルへ回します。この条件に当たるのは60件中28件です。

実測で、Dが28件の範囲でEを上回らない場合は、モデルを起動せずにEとB2で判断します。費用と遅延が0になるためです。AIを必ず起動する設計にはしません。

## 6. 限界

信頼性の確認（正解ラベルの漏えい、固定ルールの再計算、偏りの要因）と、独立再判定のための資料は [ADAPTIVE_HOLDOUT_V2_AUDIT.md](ADAPTIVE_HOLDOUT_V2_AUDIT.md) にまとめています。Codex版との比較は [CODEX_HOLDOUT_COMPARISON.md](CODEX_HOLDOUT_COMPARISON.md) にあります。

- 作成者は、規則を書いた後に条件を作りました。Eの誤りは作成者が意図して作ったものです。メモの有無と正解には相関があります（57%と28%）。方式Dの指示文には、データの設計を反映した助言が入っています。

- 60条件は評価設計上の目安です。信頼区間は広く、統計的な性能保証にはなりません。
- 正解ラベルと規則を同じエージェントが作成しています。独立した人間によるラベルの再判定が必要です（`truth.json` の `rationale_ja` を見ずに判定してもらうことを推奨します）。
- 検査カタログにCORSやCookie専用の能動的な検査がないため、これらの分類でAIにできるのは「再取得するか、しないか」だけです。カタログの追加は別途の安全審査が必要です。
- 実サイトでのメモの書かれ方、言語、長さは未調査です。
