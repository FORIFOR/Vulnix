# 診断ループ（観測 → 仮説 → 追加検査 → 再判断）の実装計画

2026-11-20 作成。外部レビュー（第2〜4段階）を受けた計画です。まだ実装していません。

## 目標

隔離した1つの API ラボで、次の工程を最後まで通します。

> 観測 → 認可の仮説 → 追加検査 → 反証を含む再判断 → 所見 → 修正 → 同じ条件での再確認

同じ情報・同じ検査カタログ・同じ予算の固定ルールと比べて、AI の価値を測ります。

## 既存の資産（作り直さないもの）

| 資産 | 場所 | 使い方 |
| --- | --- | --- |
| 再計画ループの骨組み | `aegis/adaptive_plan_runner.py`・`adaptive_plan_state.py`（PR #93） | 計画 → 承認 → 実行 → 証拠記録 → 観測し直し、の状態機械。停止・失効・予算・重複検査の打ち切りを持つ。これを拡張する |

| 修正手順の承認済み一覧 | `aegis/advisor_catalog.py` の `REMEDIATION_ACTIONS`・`OPERATIONS` | 修正と再確認は ID で指定する |

## 現状の欠け（2026-11-20 の確認）

1. **再計画の入力に、検査結果の意味が入っていない。** `plan_with_artex` が ARTEX に渡す観測は、所見のタイトル一覧と、一部の固定観測だけ。どの検査が仮説を支持・反証・判断不能にしたかは渡していない。
2. **仮説の記録がない。** 「怪しいがまだ分からない」状態を、所見とは別に持てない。
3. **計画の出力を自由文から推定している。** `artex_bridge.classify()` がキーワードで検査を当てている。検査 ID を明示する契約になっていない。
4. **ラボの条件が2つ足りない。** 「本人の資源だけ取得できる」と「仕様が足りず判断できない」。

## 第2段階：観測と仮説を、所見と別に持つ

新しい小さなモジュール `aegis/diagnosis_state.py` に置きます。`assessment.py` には足しません。

| データ | 内容 |
| --- | --- |
| `Observation` | 何を観測したか、出所（固定 L1・所有者の仕様・検査結果）、証拠 ID、対象 ID、時刻 |
| `Hypothesis` | 問題かもしれない内容（ID・対象・前提）、状態（`open`・`supported`・`contradicted`・`inconclusive`・`needs_spec`）、支持と反証の証拠 ID |
| `PlanStep` | 検査 ID、仮説 ID、参照する証拠 ID、選んだ理由（固定の選択肢から） |
| `StepResult` | 実行結果、追加された観測、仮説への効果（支持・反証・不明） |

- 仮説の状態を変えるのは Vulnix の判定器だけにします。モデルの文章では変えません。
- `Finding` に上げるのは、`supported` で、証拠の条件がそろったものだけです。

テスト（先に書く）：
- 状態遷移が正しいこと（反証された仮説は再び `open` に戻らない）。
- 証拠 ID のない支持や反証を受け付けないこと。
- 外部に出す表現に、秘密値（Cookie・本文・URL）が入らないこと。

## 第3段階：結果を受けて再計画する

- **計画の契約**：ARTEX には `{hypothesis_id, catalog_id, target_ref, evidence_refs, reason}` で答えさせます。
  - ID が一覧にない応答や、引数が範囲外の応答は、棄却します。
  - `classify()` のキーワード推定は、古い出力との互換のためだけに残します。
- **ループ**：`AdaptivePlanRunner` の各周回で、次を行います。
  - 未解決の仮説と最新の観測を、匿名の ID で渡します。
  - 結果を判定器にかけ、仮説の状態を更新します。
- **打ち切り**：
  - 未解決の仮説がなくなったとき。
  - 同じ証拠で同じ検査を選んだとき。
  - 仕様が足りないとき（`needs_spec` で止め、「確認が必要」と表示）。
  - 回数・時間・費用の上限に達したとき。
  - 停止・失効・対象の変更があったとき。
- **記録**：計画と結果は消さずに残し、どの結果がどの仮説を動かしたかの因果を監査に残します。

## 第4段階：1つの認可シナリオで、AI の効果まで測る

- **ラボ**：既存の7条件に2条件を足します。正解表は別ファイルにし、診断コードからは読みません。
  - 本人の資源だけ取得できる。
  - 仕様が足りず判断できない。
- **比較する3方式**：初期観測・検査カタログ・権限・通信量・時間・費用の上限をそろえます。
  1. 現行の固定 L1
  2. 観測に応じて選ぶ固定ルール＋追加検査
  3. 実 ARTEX＋実モデル＋同じ追加検査カタログ
- **測る指標**：
  - 正しく見つけた数・誤検知・見逃し・判断不能
  - 対象への GET 回数・時間・費用
  - 反証によって仮説を棄却できた数
- **評価用の条件の分け方**：開発に使った条件は回帰テスト用に回し、未知の条件を別に残します。
- **実モデルでの測定**：有料のため、送信する要求の SHA と費用の上限を決めて、所有者の承認を1回ごとに得ます。

## 第5段階との関係

実サイトの L1 は、URL 登録 → 所有確認 → 読み取り診断 → 修正 → 同じ条件での再測定、までを別に仕上げます。

- 実サイトの L1 には、今はこの「同じ条件での再測定」がありません。
- 再測定の結果は「再検出」「観測しなかった」「測定できなかった」「条件が変わり比較できない」の4つに分けます。
- 「取得できなかった」を「修正済み」として扱いません。
