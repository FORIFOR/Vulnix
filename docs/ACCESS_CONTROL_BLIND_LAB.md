# 認証・アクセス制御のブラインド比較（Draft PR #67）

## 正解と計画入力の分離

14条件のHTTP対象は `tests/fixtures/access_control_lab.py`、脆弱性と検査適否の正解は `tests/fixtures/access_control_truth.json`、所有者が提供した認証要件は `tests/fixtures/access_control_owner_specs.json` に分けた。HTTP対象と正解表はVulnixの診断コードを参照しない。計画生成への入力は、ルートGETから測ったアカウント資源リンクの有無だけであり、モード名、正解表、応答本文、秘密マーカーは渡さない。ローカル模擬モデルはリンクがある場合にIDORを提案する。これは実モデルの判断力を示すものではない。

独立した検査適否ラベルは「認証を要するアカウント別資源に対する境界検証が必要か」を意味し、「脆弱性があるか」とは別である。公開アカウント一覧にも同じリンクを置き、単純な観測だけでは不要な検査を1件選ぶ条件を含めた。未認証公開、403、404、紛らわしい200、所有者側資源欠落、認証必須の正常応答も含めている。

## 所有者仕様と判定

既存のサイト別L2プロファイルに任意の `root_access` を追加した。値は `requirement`（`public` または `authentication_required`）、`spec_status`、`spec_evidence` の3項目だけ。`confirmed` には仕様の根拠が必須で、サイトプロファイルは従来どおり管理者が内容のハッシュを承認しなければ `unaccepted` になる。所有確認済み対象のルートGET以外には適用しない。

- `public` と確認済み：JSON 200だけではアクセス制御所見を出さない。
- `authentication_required` と確認済み：未認証JSON 200を `detected` とする。根拠は所有者の認証要件と実際のHTTP応答。応答内容の機密性、他ユーザー情報の取得は未実証と明示する。
- 仕様なし、未確認、未承認：`candidate` を維持する。

このL1判定は実サイトに追加GETを行わない。実サイトのL2禁止も維持する。

## IDORの独立した実行証拠

隔離ラボのWorkerは、まずBとしてBの固定資源をGETし、資源ID・所有者・マーカーが一致するか確認する。成立しなければAのGETを行わず `unverified` とする。成立した場合のみAとして同じ資源をGETし、Aの呼出元、Bの所有者、同じ資源ID、マーカー、HTTP 200が揃ったとき `proven` にする。403を `not_reproduced` とするにもBの対照実行、固定パス、Aの要求、Worker判定の一致を要する。404や紛らわしい200は安全とも脆弱とも断定しない。
