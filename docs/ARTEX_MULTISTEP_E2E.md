# 多段階ARTEX計画（状態機械）の実装と検証

2026-11-19 JST。検証はローカルの模擬ラボ（ループバック）だけで行い、実サイトへの通信と有料APIの呼び出しはともに0回。

## 1. 構成

| ファイル | 役割 |
| --- | --- |
| `aegis/adaptive_plan_state.py` | 状態、許可される遷移、上限（`PlanLimits`）、遷移の記録 |
| `aegis/adaptive_plan_runner.py` | 既存の `plan_with_artex` と `execute_artex_item` を1段階ずつ呼び出す |
| `tests/test_adaptive_plan_runner.py` | 状態機械、正常系、異常系（21件。実ARTEXのテスト1件を含む） |

ランナーは新しい権限を持ちません。

- トークン、承認、Workerの起動手段のいずれも保持しません。
- 各段階は、利用者が操作したときと同じ経路を通ります。
  - 計画：ARTEX → `reconstruct` → `ProposalRouter`
  - 実行：Gateway → Worker
- 既存の安全制御はそのまま働きます。所有確認、範囲、L2の承認（依頼者と承認者の分離）、隔離、緊急停止、監査が対象です。

## 2. 状態遷移

```
CREATED → OBSERVED → PROPOSED → AUTHORIZED → EXECUTING → EVIDENCE_RECORDED
             ↑                                                   │
             └────────────── 再観測（次の段階） ───────────────────┘
PROPOSED / EVIDENCE_RECORDED → COMPLETED
終了していない状態 → REJECTED | CANCELLED | EXPIRED | FAILED
```

各遷移で記録する項目：

- 計画ID
- 診断の世代（`_run_generation`）
- 権限台帳の世代（`ledger.generation`）
- 段階ごとの承認ノンス
- カタログID と 項目ID
- 残りの予算（段階数、計画回数、秒数、計画の費用、Gatewayの実行回数）
- 監査ハッシュ
- 証拠ID

遷移は**先に監査へ書き込みます**。監査に書けなければその遷移は起きず、計画は `FAILED` になります。

## 3. 安全上の規則

- **1段階で実行する検査は1つです。** 次の計画を立てるのは、その段階の証拠を保存した後だけです。新しい計画は、その時点の所見を入力にします（再観測）。
- **承認は引き継ぎません。**
  - L2の項目は、そのたびに `approve` コールバックで人間の承認を得ます。これが承認を引き継がないことの実際の保証です。
  - 段階ごとの承認ノンスは、監査記録を段階と結び付けるための**ラベル**です。サービス側では検証しないため、それ自体は権限ではありません。
  - 依頼者が自分の依頼を承認しようとした場合は、既存のサービスが拒否します。
- **同じ検査は繰り返しません。** この計画で実行済みのカタログIDは二度と実行しません。重複した件数は `duplicates` に記録します。
- **上限を設けています。** 既定値と、その下で働く既存の上限は次のとおりです。

  | 上限 | 既定値・内容 |
  | --- | --- |
  | `max_steps` | 3 |
  | `max_planner_rounds` | 5 |
  | `max_seconds` | 300 |
  | `max_planner_cost_usd` | 0.10 |
  | Gatewayの実行回数 | `Budget(50)`（既存） |
  | Planner LLM Gateway | 呼び出し回数・トークン・費用の上限（既存） |

- **計画の前と実行の直前に再確認します。** 対象は次の4点です。
  - 停止・リセット（世代とGatewayの状態）
  - 一時停止
  - 要求者の権限（ログアウトや組織からの除名。サーバーの `live_request_authority` を渡す）
  - 期限
- **実行の後にも再確認します。** 停止や失効の後に届いた結果は採用しません。
  - 停止された場合：既存の `_exec` が結果を捨てます。
  - 要求者の権限が失効した場合（今回追加）：`AssessmentService._exec` がWorkerの戻りの直後に `request_authorized()` を再確認します。失効していれば、結果を所見に反映せずに `result.discarded` を監査に記録します。そのうえで `ApproverRequired` を返し（HTTPでは403）、項目を `failed` にします。
  - この再確認は、利用者の要求で動く `execute_artex_item` と `verify_finding` の経路だけに働きます。バックグラウンドで実行中の初回診断の挙動は変えていません。
- **証拠の整合を確認します。** 次のどれかに当たれば、計画は `FAILED` になります。
  - その段階で新しい監査 `result` が1件もない
  - その段階で所見に増えた証拠が、その段階の `result` に含まれない
  - 監査チェーンが壊れている

## 4. 異常系の検証結果

| 条件 | 期待する結果 | 結果 |
| --- | --- | --- |

### 既存の仕様との整合

- **起動前の確認との一貫性**：同じ要求者の権限確認（`self._tls.request_authorized`）を、既存の `_late_launch_guard` はWorkerの起動前に使っています。今回の修正は、同じ確認を「結果を採用する前」にも行うものです。
- **影響範囲**：この値が設定されるのは、利用者の要求で動く `execute_artex_item` と `verify_finding` だけです。バックグラウンドの初回診断（`_run`）では設定されないため、挙動は変わりません。
- **例外を送出した後の後始末**：
  - L2経路では、`finally` で承認を取り消します。
  - ARTEXの項目は `failed` になります。
  - `verify_finding` の `finally` で、スレッドの状態と操作中の印を元に戻します。
- **全件テストでの確認**：既存の仕様テストは13のクラスに継承されています。全件テストでの結果は §7 に記載します。
