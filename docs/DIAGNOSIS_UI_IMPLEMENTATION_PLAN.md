# 診断ループの画面：設計レビューと実装の PR 計画

2026-11-21。[DIAGNOSIS_UI_DESIGN.md](DIAGNOSIS_UI_DESIGN.md) を、実装の前提（組織の分離、認証、監査の証拠の検証）から見直しました。その結果と、次の PR の分け方をまとめます。

## 1. 設計レビューで見つかった前提の不足

| # | 不足 | 影響 | 対応 |
| --- | --- | --- | --- |
| 1 | `DiagnosisState` は呼び出し元が持つ、メモリ上のオブジェクトです。評価（assessment）ごとに保存されず、再起動すると消えます。 | 表示 API が読む「正本」がありません。 | PR-A で、評価ごとに1つ、サービスの中に持ちます。実行世代とルート URL に結びつけ（PR #97 の `bind`）、作業領域のリセットで捨てます。 |
| 2 | 所有者の仕様（`record_owner_spec`）は、監査に記録していません。 | 判定の根拠のうち、仕様だけが監査で確かめられません。画面からの入力も、誰が入れたか残りません。 | PR-A で、`diagnosis.owner_spec` として、記録者・役割・対象・値を監査に書いてから状態に反映します（書けなければ反映しません）。 |
| 3 | 表示用のデータには、監査の鎖が検証できているかの情報がありません。 | 改ざんされた記録を、正しいものとして表示する恐れがあります。 | API で `audit.verified_entries()` を確かめます。各判定の `result_audit_hash` と `judged_audit_hash` が検証済みの記録にあるときだけ、手順を表示します。鎖が壊れていれば、手順を出さず「記録を確かめられません」とします。 |
| 4 | 修正後の確認を、画面から始める操作の権限が決まっていません。 | 依頼者以外が始めたり、失効した後に始めたりできてしまいます。 | PR-C で、依頼者の役割と、要求時点での権限の確認（`request_authorized`）を必須にし、`begin_fix_check(..., request_authorized=...)` を使います。 |
| 5 | 実サイトでの表示の扱いが、文章だけで決まっていません。 | 実サイトの評価に、空の区画やエラーが出ます。 | API は、`diagnosis_targets()` が空の評価（実サイト・所有確認中）では `404` を返し、画面は区画を表示しません。 |

## 2. PR の分け方

### PR-A：バックエンドの表示 API（ラボ専用・読み取りだけ）

**変更点**
- `AssessmentService` に、評価ごとの `DiagnosisState` を持たせます（実行世代とルートに結びつけ、リセットで捨てます）。
- 所有者の仕様を監査に記録します（`diagnosis.owner_spec`）。
- `diagnosis_view()` を追加します。設計書の `DiagnosisView` を、監査で検証できた事実だけから組み立てます。
- `GET /api/assessments/{id}/diagnosis` を追加します。組織の経路なので、`_get_org` → `_dispatch` → `_bind` を通します。
- SSE で `diagnosis.updated` を送ります。中身は `DiagnosisView` と同じです。

**必須のテスト**
- `tests/test_tenancy.py`：他の組織のメンバーは、GET も SSE も読めないこと（404）。ログインしていなければ 401 になること。
- 実サイトと所有確認中の評価では 404 になり、計画も作られないこと。
- 監査の記録を1件書き換えると、手順を表示しないこと。
- 返す内容に、ARTEX の intent 本文、advisory の文、生の応答本文、モデルのトークンが含まれないこと（PR #97 の、計画者への入力を確かめるテストと同じ方法で確かめます）。
- 仕様の監査に失敗すると、状態が変わらないこと。

### PR-B：画面（読み取りだけ）

**変更点**
- `src/lib/labels.ts` に、設計書 §4 の対応表を追加します。
- `src/lib/types.ts` に `DiagnosisView` を追加します。
- `assessmentEvents.applyEvent` で `diagnosis.updated` を取り込みます。
- `DiagnosisLoopPanel` を作り、`ArtexPlanPanel` の下に置きます。

**必須のテスト**
- `labels.test.mjs`：すべての claim、state、catalog、reason、rule、終了理由に文言があること。文言が空でないこと。色だけで表していないこと（文言の対応があること）。
- `assessmentEvents.test.mjs`：`diagnosis.updated` の取り込み、`seq` の欠けがあったときの再取得。
- `npm test`、`npm run lint`、`npm run build` がすべて通ること。
- ラボで E2E を通し、反証 → 再計画 → 支持 → 修正後の確認を画面に表示した状態のスクリーンショットを、PR に添えます。

### PR-C：操作（仕様の入力と、修正後の確認の開始）

**変更点**
- `POST /api/assessments/{id}/diagnosis/owner-spec`：所有者の役割だけが使えます。値は `authentication_required` か `public` のどちらかです。監査に書いてから反映します。
- `POST /api/assessments/{id}/diagnosis/fix-check`：依頼者だけが使えます。要求時点の権限を確かめ、監査に書きます。L2 は、これまでどおり項目ごとに人の承認が要ります。

**必須のテスト**
- 組織の分離。
- 役割のない利用者には 403 を返すこと。
- 権限が失効した後の操作を拒否すること。
- 緊急停止中は拒否すること。
- 二重に送っても、修正後の確認が2つにならないこと。
- 実サイトでは 404 を返すこと。

## 3. 守ること（すべての PR に共通）

- 表示するのは、監査で検証できた事実と、決まった ID の文言だけです。モデルの推論文は表示しません。
- L2 の承認は、既存の `ApprovalCard` だけで行います（依頼者と承認者を分けます）。
- 実サイトへの通信、外部モデルへの送信、公開βへの反映はしません。
