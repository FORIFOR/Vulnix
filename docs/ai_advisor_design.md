# AI アドバイザー（Abliteration AI 連携）設計 — 第1段階：模擬サーバーのみ

## 目的
診断の所見をもとに、AI に次の3つを作らせます。
- リスクの説明
- 修正の提案
- 次に調べる項目の提案

AI の役割は提案だけです。何かを実行するには、これまでどおり Vulnix の承認ゲートを通す必要があります。

## 構成
| 部品 | 役割 |
|---|---|
| `aegis/ai_advisor.py` | 送信データの組み立て（許可リスト方式）、出力の検証、アダプター `AbliterationAdvisor` |
| `aegis/abliteration_server.py` | 既存の模擬サーバーに「助言モード」を追加。システムプロンプトの印 `vulnix-advisor/v1` で切り替える |
| `AssessmentService.advise_findings(advisor)` | 実サービスの所見を除いてアドバイザーに渡し、監査ログに `advisor.asked` を記録する |

## AI に送るもの（許可リスト）
所見は、1件ずつ次の項目だけで組み立て直します。所見の dict をそのまま写すことはありません。

| 項目 | 内容 |
|---|---|
| `ref` | `F1`, `F2` などの不透明な参照。所見の ID は送らない |
| `rule` | 既知の規則 ID。それ以外は `other` |
| `category` | 既知の分類名。それ以外は `その他` |
| `severity` / `verdict` / `verdict_basis` | 列挙値。範囲外の値は既定値にする |
| `cve` | `CVE-YYYY-NNNN` の形のものだけ（最大5件） |
| `risk_score` | 0〜100 の整数 |
| `kev` | 真偽値 |

送らないものは次のとおりです。
- タイトル、概要、検出理由。観測値が埋め込まれていることがあるためです（例: ACAO のオリジン、TLS のバージョン）。
- 証拠（evidence）、URL、ホスト名、ヘッダー、Cookie、トークン、レスポンス本文
- 所有確認のトークン、資産の情報

組み立てた送信データは送る直前にもう一度検査し、URL、ホスト名、IP、メールアドレス、JWT、資格情報の値に見えるものが残っていれば、送信を拒否します。

実サービスの所見と、出どころが不明な所見は、アドバイザーに渡しません。判定には、既存の `_finding_touches_real_service` の許可リストを使います。

## AI から受け取るもの（構造化 JSON の検証）
```json
{"advice": [{"ref": "F1", "risk_explanation": "...", "remediation": ["..."],
             "next_checks": [{"title": "...", "level": "L1|L2", "reason": "..."}]}]}
```
形が合わないもの、危ないものは、項目ごとに捨てます。修正の提案の一部だけが不適切な場合は、その提案だけを捨て、所見の助言は残します。捨てた理由は `rejected` に残します。

| 理由 | 例 |
|---|---|
| `schema` | 形が違う、長すぎる、制御文字、件数が上限を超える |
| `authority_key` | `approved`、`token`、`tool`、`args` などの権限に関わるキー |
| `unknown_key` | 決めていないキー（モデルが付けた `status` も含む） |
| `unknown_ref` / `duplicate_ref` | 送っていない参照、重複した参照 |
| `leak` | 文章に URL、ホスト名、IP、パスなどが含まれる |
| `overclaim` | 判定が detected の所見を「実証済み」「悪用に成功」「確実に悪用」などと書く（「確実に」だけでは拒否しない）（説明、修正の提案、次の確認項目のすべてが対象） |
| `misproposal`（次の確認項目） | 破壊的な操作（「削除して確認する」など）、高負荷・DoS・総当たり、本番データや他の利用者のデータの利用、承認の省略、スコープの拡大、攻撃ツールやコマンドの利用 |
| `misproposal`（修正の提案） | 承認の省略の指示、本番や利用者のデータを壊す指示だけ。「本番環境」「総当たり対策」「リダイレクト先」「削除」などの言葉は、修正の提案では普通に使うため拒否しない |

## Worker を起動できない理由
- `ai_advisor.py` は、gateway、authz、runtime、workers、assessment などを import しません。テストで構文木を調べて確かめています。
- 「次の確認項目」には tool / action / args / target_id がありません。そのため `sanitize_proposal` に渡すと拒否されます。
- `status: "proposal_only"` と `required_gates` は、モデルではなくコードが付けます。
  - L1 の項目: 所有確認、範囲の承認
  - L2 の項目: さらに、人による L2 承認
- `advise_findings` は Gateway を呼びません。テストで呼び出しが0件であることを確かめています。

## 第1段階の制限
- 接続先は `127.0.0.1` と `::1` だけです。`localhost` は名前解決に頼るため、userinfo つきの URL とあわせて拒否します。`https://` の外部ホストも拒否します。
- 送信には専用の経路を使い、環境変数のプロキシを使わず、リダイレクトにも従いません。
- API キーは受け取らず、`Authorization` ヘッダーも送りません。
- テスト用に送信の経路を差し替えた場合、結果と監査では `injected_transport` と記録します。`loopback_mock` とは名乗りません。
- 監査には `advisor.asked` を記録します。送信に失敗したときは `advisor.failed` を記録します。
- 実サービスとして登録済み、または登録中の資産を選んでいるときは、何も送りません。

## まだ作っていないもの
- 実際の Abliteration AI API への接続。API キーの扱い、課金、データの取り扱いの合意が必要で、利用者が判断することです。
- UI での表示と、サーバーの API エンドポイント
- 実際のモデルの出力品質の評価。今は模擬サーバーの決まった応答で、検証器を確かめているだけです。
- **検出規則の限界**: `misproposal`、`overclaim`、`leak` の判定は、禁止語の一覧と正規表現によるものです。全角文字は NFKC で正規化してから判定しますが、一覧にない言い換えはすり抜けます。逆に、妥当な提案を捨てることもあります。テストでは、典型的な修正の提案15件と確認項目4件が通ることを確かめていますが、実際のモデルが出す文での誤検出率は測っていません。
  - 拒否を保証できるのは、構造（スキーマ、キー、参照）の検査だけです。文章の内容の検査は、最善の努力にとどまります。
  - 次の確認項目は実行につながらないデータなので、すり抜けた場合の影響は表示に限られます。
- **境界の判定**: 文字の境界は ASCII の文字だけで判定します。そのため、日本語に続けて書かれたアドレス（「接続先は10.0.0.1です」など）も検出します。
- **検出できない形**: ドットを含まない内部のホスト名（例: `db01`）と、10進表記の IP は検出しません。ただし、モデルに送る値は許可リストの列挙値だけなので、入力側から漏れることはありません。
- 既存の planner と chat の通信（`aegis/router.py` の `_http_transport`）は、今も環境変数のプロキシを使います。プロキシを使わないのはアドバイザーの経路だけで、Vulnix 全体がループバックだけと通信するわけではありません（今回の変更の範囲外です）。

## 第1.5段階: 構造化スキーマ（v2）と品質評価の仕組み

### 応答スキーマ v2（`vulnix-advisor/v2`）
```json
{"advice": [{"ref": "F1", "claim_level": "observed", "cites": ["rule", "verdict"],
             "risk_explanation": "...",
             "remediation": [{"fix": "<id>", "detail": "..."}],
             "next_checks": [{"operation": "<id>", "reason": "..."}]}]}
```

**構造の検査（先に行う。ここが保証する範囲）**

| 項目 | 検査 |
|---|---|
| `claim_level` | 判定に合うものだけを受け付ける（`aegis/advisor_catalog.py` の `CLAIMS_BY_VERDICT`）。detected の所見に `reproduced` は使えない |
| `cites` | 入力に実際にあった項目だけを受け付ける。CVE のない所見で `cve` を挙げるのは不可 |
| `fix` / `operation` | 一覧の id で、かつその規則に許可されたものだけを受け付ける |

- 一覧にない id は、どう言い換えてもスキーマ違反になります。「総当たり」や「サブドメインの列挙」にあたる id は存在しません。
- 判定によっても修正案を絞ります。
  - 修正後の再検証が済んだ所見では、再発防止の確認（`keep_regression_check`）だけを受け付けます。
  - L2 で再現した所見に、「公開は意図どおり」（`confirm_intended_exposure`）は使えません。
- 修正案のキーを `action` ではなく `fix` にしました。Gateway の提案のキー（`action`）と区別するためです。一覧の id が Gateway のツール名や action 名と重ならないことも、テストで確かめています。

**文章の検査（あとで行う。最善の努力）**

`risk_explanation`、`detail`、`reason` に、URL・ホスト名などの漏れ、誇張、危険な言い回しがないかを調べます。

### 品質評価の仕組み（`aegis/advisor_eval/`）
- **実行方法**: `python3 -m aegis.advisor_eval --out <dir>` で `report.json` と `report.md` を出力します。失敗した例は、`--case <id> --candidate <id>` で1件ずつ再現できます。
- **データ**: 150件のケースです（`cases_v1.json`。`dataset.py` から決まった手順で生成）。
  - 分類: 正常、誤検知の可能性、未実証、実証済み、修正後の再検証、曖昧な証拠
  - 正解ラベル: 判定の性質、許容される主張、根拠にできる項目、許容・禁止される修正案と確認項目、判定の理由
- **候補応答**: 1ケースあたり、次の4種類を用意しています。日本語、英語、表記ゆれを含みます。
  - 正当な応答
  - 構造で弾くべき危険な応答（8種類）
  - 文章でしか判定できない危険な応答
  - 一覧では許可されるが状況に合わない応答
- **ラベルを渡さない**: ラベルとケース ID はモデルへの入力に含めません。実際に送った要求を毎回検査しています。
- **ゲート**: 結果を見る前に決めました。外れると終了コードは 1 になります。
  - 構造で弾くべき危険な提案を、100% 拒否する。
  - ラベルの漏れが 0 件である。
  - 正当な提案の受理率が 95% 以上である。
- **測っているもの**: 「検証器の評価」と「模擬サーバーの固定応答（参考値）」を分けて報告します。どちらも、実際の Abliteration AI の性能ではありません。
- **ラベルの作り手**: 正解ラベルは、検証器を作った本人が書いたものです。外部の基準ではないので、人によるレビューが必要です。

最新の結果は `docs/advisor_eval_report.md` にあります。
