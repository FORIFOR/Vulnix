# 診断ループの画面（PR-B・読み取りだけ）

2026-11-21。[DIAGNOSIS_UI_DESIGN.md](DIAGNOSIS_UI_DESIGN.md) と [DIAGNOSIS_UI_IMPLEMENTATION_PLAN.md](DIAGNOSIS_UI_IMPLEMENTATION_PLAN.md)（PR #99）の PR-B を実装したものです。データは PR-A（PR #100）の `GET /api/assessments/{id}/diagnosis` と SSE の `diagnosis.updated` だけから取ります。

**この PR には、状態を変える操作はありません。** 診断の開始、所有者の仕様の入力、修正後の確認の開始は PR-C で追加します。L2 の承認は、これまでどおり ARTEX 計画の項目で行います（この区画からはその項目へのリンクだけを出します）。

## 1. 表示するもの

評価の画面の「診断」タブで、ARTEX 計画の下に `DiagnosisLoopPanel` を置きます。

| 区画 | 内容 |
| --- | --- |
| 見出し | 「ラボ専用」、世代、再起動前の記録なら「再起動前の記録（読み取り専用）」 |
| 状態と次に必要なこと | 計画の状態と手順数（例：1 / 3）、次に必要なこと（L2 の承認なら承認待ちの項目へのリンク） |
| ① 確認しようとしていること | 仮説ごとに、確かめる内容・対象・世代・状態、根拠／支持／反証／判断不能の観測 ID |
| ② 手順の記録（新しい順） | 検査、確かめた仮説、なぜ（契約の理由と根拠の観測）、承認者、観測、判定と判定規則の理由、検査結果と判定の監査ハッシュ（ログのタブへのリンク）と時刻 |
| ③ 修正の前後 | 修正前と修正後の同じ検査の判定と監査ハッシュ、結果（改善を確認／改善されていない／確認中） |
| 観測の一覧 | すべての観測（開閉式） |

- 文はすべて `web/src/lib/labels.ts` の固定の対応表から作ります。表にない ID は「未定義の値（ID）」と出し、推測しません。`tests/test_diagnosis_ui_labels.py` が、バックエンドが送りうる ID（仮説の種類、状態、契約の理由、判定規則、検査、観測の種類、計画の終了理由、表示の拒否理由、次に必要なこと）をバックエンドのコードから読み、すべてに文言があることを確かめます。
- 状態は色だけでなく、必ず文字で示します。修正後の確認の仮説は、反証を「改善を確認」、支持を「改善されていない」と読み替えます。
- 修正後の確認の計画は手順を S1 から数え直すため、2世代目以降の手順は「世代 2・S1」と表示します。
- 新しい判定が届くと、`aria-live="polite"` の領域で一文だけ知らせます（例：「S2 の判定：支持（成立）」）。

## 2. 表示しない場合

| 場合 | 画面 |
| --- | --- |
| API が 404（実サイト、所有確認中） | 区画を出しません。実サイトの評価では、そもそも区画を描きません。 |
| `status: "unverified"`（監査ログを確かめられない） | 理由だけを赤い枠で示し、仮説・手順・観測・比較は1件も出しません。 |
| 応答の形が想定と違う | `invalid_response` として同じく結果を出しません。手順に検査結果と判定の監査ハッシュ（64桁）がそろっていない場合も同じです。 |
| 別の評価の内容 | `assessment_id` が違う応答やイベントは捨てます。 |
| 取得の失敗（404・401・403 以外） | 前回確かめた内容を残し、「最新の状態を取得できませんでした」と示します。 |
| 401・403 | 評価の画面全体と同じく、すべて消します。 |

## 3. SSE の欠落・再接続・重複

`lib/useAssessment.ts` の既存の同期に乗せています。

- **重複・再送**：イベントの `seq` が表示済みの番号以下なら捨てます（`eventDecision`）。再接続すると、最初の `after` から送り直されるため、この判定で落とします。
- **欠落**：番号が飛んだら、評価・監査ログ・診断の表示をまとめて取り直します。イベントが届かない間も、既存の定期的な取り直しで追いつきます。
- **取り直しとイベントの競合**：診断の表示は評価の取り直しと同じ要求で読み、取り直しの途中でイベントが届いた場合は、取り直しの結果を捨てます（既存の `shouldApplySnapshot`）。
- **サーバーの再起動**（今回直した既存の不具合）：イベントの番号はサーバーのプロセスごとに 0 から数え直します。これまでは、再起動後の評価が古いものと見なされ、画面が再読み込みまで止まっていました。モデルの状態に含まれる起動 ID（`planner.boot_id`）が変わったら、番号を忘れてイベントの受信を開き直します（`serverRestarted`）。

## 4. 確かめたこと

- `web/tests/diagnosisView.test.mjs`：結果を隠す条件、別の評価の除外、取得結果の扱い、重複・再送・欠落の判定、再起動の判定、文言、読み替え、通知の文、並び順、表の文言がそろっていること。
- `tests/test_diagnosis_ui_labels.py`：バックエンドの ID がすべて文言を持つこと（文言を1つ消すと失敗することを確かめました）。
- `scripts/check_diagnosis_ui.py`（CI の実 ARTEX のジョブで実行）：ローカルの検証ラボで、実際のコントロールプレーン・Next.js の本番ビルド・ブラウザを使い、次を確かめてスクリーンショットを残します。
  1. 未開始 → S1 反証 → L2 の承認待ち（承認者は依頼者と別）→ S2 支持。再読み込みせずに SSE で表示が変わること。390px でも横にはみ出さないこと。
  2. 修正後の確認で、修正の前後の比較が「改善を確認」になること。
  3. SSE：接続できない場合（定期的な取り直しで追いつく）、ストリームが切れて再接続する場合、偽の表示を載せた重複イベントと古いイベント（表示しない）。対照として、同じ偽の表示を新しい番号で送ると表示されることも確かめ、重複の判定が別の理由で通っていないことを示します。
  4. 別の組織のメンバー：API は 403、画面には自分の組織の空のラボだけが出ること。
  5. バックエンドの再起動：開いたままの画面が、再読み込みなしで「再起動前の記録」を表示すること（起動 ID の修正を外すと、この確認が失敗することを確かめました）。
  6. 監査ログの書き換え：理由だけを表示し、手順を1件も出さないこと。

この確認では、PR-C がまだないため、診断ループはスクリプトの中から開始します（テストと同じ方法）。L2 の承認も、承認者 `approver-human` としてスクリプトが与えます。画面からの承認・開始は PR-C の範囲です。

## 5. 独立レビューで直した点

| # | 指摘 | 修正 |
| --- | --- | --- |
| 1 | 診断の表示を評価と並行して読むと、評価より古い表示が残り、対応するイベントは「表示済み」として捨てられる | 診断の表示は、評価を読み終えた後に読む（評価の番号より古くならない） |
| 2 | 未知の修正結果を「確認中」、未知の終了理由を「整合を確認できず」と表示していた（推測） | 未知の値は「未定義の値（ID）」と状態の文言だけにする |
| 3 | 文言の網羅テストが、パターンの1つが壊れても通りうる | パターンごとに必ず1件以上見つかることを確かめる。観測の属性・修正結果も対象に加える |
| 4 | 形の崩れた `ok` の表示で、描画が例外を出して評価の画面全体が消えうる | すべての項目の型を確かめ、崩れていれば `invalid_response` として結果を出さない |
| 5 | 最初の読み込みに失敗すると、イベントの受信が開かれないまま | 最初に読み込みに成功した時点で受信を開く |
| 6 | 形の崩れた応答で「保存できていません」と誤って表示 | 応答に `persisted: false` がある場合だけ表示する |
| 7 | 評価の ID が変わったときに番号を引き継ぐ | ID ごとに番号と起動 ID を初期化する |

## 6. 残っていること

- 診断の開始、所有者の仕様の入力、修正後の確認の開始（PR-C）。
- 所見の判定の変化（`f_idor: 実証成功 → 再現せず`）を修正の前後の比較に並べること（PR-A が返していないため）。
- 監査ハッシュのリンクはログのタブへ移り、その記録の位置へスクロールします。既存の証拠表示（`EvidencePanel`）への直接の移動はまだありません。
