# パスワード変更の永続性（Password change durability）

## 問題

`OperatorStore.change_password` は、新しいハッシュをメモリに入れてから `operators.json` を書いていました。
書き込みに失敗すると、プロセス内では「両方のパスワードを拒否・ストアは信頼しない・再試行する」状態になりますが、
再試行が成功する前にプロセスが再起動すると、ファイルには**古いハッシュ**が残っているため、古いパスワードで再びサインインできました。
（再現: `_atomic_write` を `operators.json` だけ失敗させて変更 → `AuthError` → 同じパスで `OperatorStore` を作り直す → 古いパスワードでログイン成功。
`tests/test_password_change_durability.py` の `TestReproduction` が修正前に失敗することを確認済み。）

## 目標

- 失敗・中断したパスワード変更のあと、再起動・クラッシュ・脅威モデル内のファイル操作のどれでも、古いパスワードが有効に戻らない。
- 変更が成功したら、新しいパスワードだけが有効。
- 復旧に手でファイルを編集する必要がなく、復旧できないロックアウトを作らない。

## 状態の置き場所

| 置き場所 | 内容 |
|---|---|
| `operators.json` | アカウントごとの `password_hash` と、確定した `credential_generation`（整数、無い場合は 0） |
| `operators.credential-state.json`（0600、同じディレクトリ） | 進行中の変更マーカー `{"pending": {名前: {"generation": g, "reason": ...}}}`。マーカーの世代がファイルの確定世代より大きいアカウントはサインインを拒否する |
| 監査ログ（`platform-audit.jsonl`、単一組織構成では `audit.jsonl`） | 変更の意図（`account`, `credential_generation`, `hash_digest` = 新しいハッシュ文字列の SHA-256。ハッシュ自体は書かない）、中止（`auth.credential_change_aborted` に `account`/`credential_generation`/`hash_digest`。同じアカウント・世代・digest の意図だけを取り消す。ハッシュは毎回新しいソルトなので、再起動後に世代が再利用されても別の変更を取り消さない）、完了（`auth.password_change_committed`）。意図と中止はアンカー対象の記録（`ANCHORED_EVENTS`） |

進行中マーカーを `operators.json` 本体ではなく別ファイルに置くのは、既存の保証
（`operators.json` が書けないときは、変更をメモリに残して「両方拒否・信頼しない・再試行」する。`test_unsaved_password_change_and_restart`）
を保ったまま、「第1段階が書けなければ何も変えない」を区別するためです。第1段階は別ファイルへの書き込みなので、
`operators.json` だけが書けない状況では第1段階は成功し、第2段階が失敗する、という扱いになります。

書き込みはすべて一時ファイル → fsync → rename → ディレクトリ fsync（`OperatorStore._atomic_write`）です。

## 手順（変更者本人の変更・管理者のリセット・オフライン復旧で共通）

0. 事前確認: 現在のパスワード（本人の変更のみ）、長さ、ストアが信頼できること（未保存の変更が残っていれば先に再試行。だめなら開始しない）、
   アカウントがブロック中でないこと（本人の変更のみ。ブロック中は古いパスワードでは解除できない）。
1. **監査の意図を先に記録**（O5 の `journal=` フック）。新しい世代 `g = max(ファイルの世代, マーカーの世代, 起動時に監査で見た世代) + 1`。
   記録できなければ何も変えない（503 `audit_failed`）。
2. **第1段階（ブロック）**: マーカー `{generation: g}` を `operators.credential-state.json` に原子的に書く。
   以後このアカウントは、確定世代が `g` 以上になるまでサインイン拒否。古いハッシュはディスクに残るが使えない。
   書けなければメモリを元に戻し `ChangeNotSaved` → サーバーは `auth.credential_change_aborted`（`account`, `credential_generation`, `hash_digest` 付き）を記録する。
   監査の記録はディスクに書けたのにリスナーやアンカーへの登録が失敗した場合も、同じ中止の記録を書いてから変更を拒否する（再起動後に黙ってロックしない）。
   古いパスワードはそのまま使え、何も変わらない。
3. **第2段階（確定）**: 新しいハッシュと世代 `g` を `operators.json` に原子的に書き、成功したらマーカーを消す（マーカーの消去に失敗しても、
   世代 `g` ≦ 確定世代なので無害。次の書き込みで消える）。対象アカウントの他のセッションは失効させる。
   書けなければ従来どおり: メモリでは新しいハッシュ、ストアは信頼しない（全員の新規サインイン拒否）、`trusted()` が再試行する。
   ディスクは第1段階のままなので、再起動すると**そのアカウントはサインイン拒否**（古いパスワードは復活しない）。
   再試行が成功すると、新しいパスワードだけが有効になり、`auth.password_change_committed` が `recovery_events` 経由で記録される。
4. **完了の記録**: 直接成功したときはサーバーが `auth.password_change_committed` を記録する（失敗しても変更は有効。意図の記録が既にある）。

### 中断点ごとの結果（再起動後）

| 中断した位置 | ディスク | 起動時の判定 |
|---|---|---|
| 監査の意図を書いた直後 | マーカー無し・世代 g-1 | 監査の世代 g > ファイルの世代 → ブロック |
| 第1段階の一時ファイルを書いた後・rename 前 | 同上 | ブロック |
| rename 後・ディレクトリ fsync 前 | マーカー g（または失われて上と同じ） | ブロック |
| 第1段階と第2段階の間 | マーカー g・世代 g-1 | ブロック |
| 第2段階の後・完了の記録前 | 世代 g・新しいハッシュ | 新しいパスワードだけ有効 |

## ロールバック・欠落・破損の検出（起動時）

サーバー（`_build_server`）は `OperatorStore(seed, credential_generations=credential_history_reader(data, default_log=svc.audit))` を渡します。
読むのは**いまの構成がアカウントの記録を書くログ**（既定のマルチテナントでは `platform-audit.jsonl`、`VULNIX_MULTI_TENANT=0` では `audit.jsonl`）と、
存在すればもう一方（以前の構成の履歴）です。監査アンカーが設定されていれば、`platform-audit.jsonl` も既定のログと同じアンカーに
別のソース ID（`<名前>:platform-audit.jsonl`）で登録され、読む前にアンカーと照合します。
アカウントごとに、中止されていない意図の最大世代 `a`（とその `hash_digest`）を求め、ファイルの確定世代 `d` と比べます。

| 状態 | 結果 |
|---|---|
| `a > d`（古いコピーへの巻き戻し、第1段階の欠落、マーカーの削除） | そのアカウントをブロック（`behind_audit`） |
| `a == d > 0` でハッシュの SHA-256 が `hash_digest` と違う | ブロック（`hash_mismatch`。マーカーだけ手で消して世代を合わせたなど） |
| `d > 0` なのに監査に記録が無い（ログが消えた・別物に差し替えられた） | ブロック（`history_missing`） |
| `0 < a < d` | 許容（ファイルの方が新しい。古いパスワードの復活ではない） |
| 読むべきログのどれかが解析できない（壊れた行、無関係なファイルの中身など） | **起動しない**（`CredentialStateUnverifiable`。メッセージで復旧手順を案内）。どのアカウントも検証できない状態でサインインさせない |
| アンカーと一致しない（`rollback` / `fork` / `chain_invalid` / `anchor_regressed` / `symlink`） | 全アカウントをブロック（証拠があるのでマーカーファイルに記録） |
| アンカーに接続できない・設定不備 | 全アカウントをブロック（この起動の間だけ。アンカーが戻ってから再起動すれば解除） |

- アンカーのあるログでは、アンカー済みの先頭より後ろに追記された中止の記録は無視します（追記だけで意図を取り消せないように）。
- 上の表で「ブロック」としたものは、マーカーファイルにも記録します（現在の世代より大きい世代のマーカー）。
  監査の確認を行わずにストアを開いても、管理者のリセットかオフライン復旧で新しい世代が書かれるまで拒否が続きます。
- 監査の連鎖が壊れていても、アンカーが無ければ解析できる記録の最大値を使います（連鎖の検証では末尾の削除は検出できず、その検出はアンカーの役割）。
- 進行中マーカーのファイルが解析できない → すべてのアカウントにマーカーを付けてブロック。オフライン復旧で管理者を戻し、管理者が他をリセットする。
- `operators.json` が解析できない → 従来どおり `OperatorStore` の生成が例外 → サーバーは起動しない。
- `operators.json` が削除された → 従来どおり、ランダムな初期パスワードで既定アカウントを作り直し、`operators.initial-credentials.txt`（0600）に書く。
  古いパスワードはどれも使えない。作り直したアカウントの世代は監査・マーカーの最大値 + 1。
- 監査に記録のある名前で新しくアカウントを作る（作り直し後の自己登録・管理者による作成）と、その世代は記録の最大値 + 1 から始まり、
  作成の監査記録（`auth.registered` / `operator.created`）にその世代と digest を残します。次回起動で誤ってブロックされず、
  以前の同名アカウントを含む古いファイルへの巻き戻しは `behind_audit` で検出されます。

ブロック中のアカウントのセッションは、起動時に読み込まず、プロセス内でも解決しません。

`credential_generations` を渡さずに `OperatorStore` を作った場合（ライブラリとしての利用・単体テスト）は、
マーカーによる保護だけが働き、監査との突き合わせは行いません。サーバーとオフライン復旧は常に渡します。

## 復旧（ロックアウトを作らない）

### (a) 管理者によるリセット

`POST /api/operators/reset-password` `{"name": 対象, "password": 新しいパスワード}`（管理者のみ。自分自身は不可 → 本人は通常の変更を使う）。
上と同じ「監査が先・2段階」で新しいパスワードと新しい世代を書き、ブロック（マーカー・不整合）を解除し、対象の全セッションを失効させます。
監査に記録できなければ 503 で何も変えません。新しいパスワードは管理者が対象者に安全な経路で伝え、対象者はサインイン後に変更します。

### (b) オフライン復旧（サインインできる管理者がいないとき）

```
# 1. コントロールプレーンを止める（データディレクトリの .lock を保持している間は実行を拒否します）
# 2. ホスト上で（データディレクトリの所有者として）
python3 -m scripts.recover_account --data-dir <データディレクトリ> --account <名前>
# 3. 表示されたファイル（operators.recovery-credentials.txt、0600）で一時パスワードを確認する
# 4. コントロールプレーンを起動し、そのアカウントでサインインして直ちにパスワードを変更し、ファイルを削除する
```

このコマンドはデータディレクトリの `.lock` を排他で取れない場合（サーバーが動いている）実行しません。
前回の `operators.recovery-credentials.txt` が残っている場合も実行しません（新しいファイルは `O_EXCL|O_NOFOLLOW`、0600 で作成）。
記録はいまの構成がアカウントの記録を書くログに書きます（アンカーが環境変数で設定されていればアンカーに登録）。
復旧したアカウントと管理者のリセットは、そのアカウントのログイン失敗によるロックも解除します。

**監査ログが解析できずサーバーが起動しない場合**は `--quarantine-unreadable-audit` を付けます。解析できないログを
`<名前>.quarantined-<時刻>` に退避し（削除しません）、新しいログに `audit.log_quarantined`（退避先・SHA-256）を記録したうえで、
**全アカウントをブロック**してから指定のアカウントだけを復旧します（履歴が検証できないので、他のアカウントは管理者がリセットする）。
アンカーのあるログを退避すると、アンカーとの照合は `rollback` になります。その場合は先に `docs/AUDIT_ANCHOR.md` の手順でアンカーのソースを扱ってください
（アンカーを使わない限り、このコマンドの意図の記録もアンカーに拒否されるため、何も変わりません）。
一時パスワードを生成し、監査ログに `auth.account_recovered_offline`（意図、世代・ハッシュの digest 付き）を記録してから 2 段階で書き込み、
完了を記録します。監査に記録できなければ何も変えません。対象アカウントのセッションはすべて失効します。
2要素認証は変更しません（認証器を失った場合は、復旧した管理者が `reset-mfa` で別の管理者の 2 要素をリセットする既存の手順）。

## 対象外・残るリスク

- **アンカーの無い構成で、監査ログを削除（または意図より前に切り詰め）し、`operators.json` を古いコピーに戻し、マーカーファイルも消せる者**:
  `d == 0` かつ監査に記録が無い状態は「変更したことのないアカウント」と区別できず、**古いパスワードが復活します**。
  データディレクトリへの書き込み権限が必要です。これを検出できるのは監査アンカーだけです（`docs/AUDIT_ANCHOR.md`）。
  アンカーを設定すれば、`platform-audit.jsonl` と `audit.jsonl` の削除・切り詰め・分岐は起動時に検出され、全アカウントがブロックされます。
- **アンカーごと巻き戻せる者**（アンカーのユーザーや root）: 対象外です。
- **`operators.json` に任意の内容を書ける者**: 好きなハッシュを書けるので対象外です。
  この仕組みが防ぐのは、クラッシュ・書き込み失敗・古いバックアップやスナップショットの復元・マーカーの欠落・使っていないログへのゴミの混入です。
- 完了の記録（`auth.password_change_committed`）はアンカー対象にしていません。消えても古いパスワードは復活せず（意図がアンカー済み）、
  アンカー対象にするとアンカーの一時的な不調でログイン処理（`recovery_events` の書き出し）が失敗するためです。
- ディレクトリ fsync の失敗は無視しています（rename は行われている）。rename が失われた場合も、監査の意図があるのでブロック側に倒れます。
- 第1段階の書き込みに失敗し、さらに中止の記録も書けなかった場合、プロセス内では古いパスワードが使えますが、
  再起動後はそのアカウントがブロックされます（フェイルクローズ。管理者リセットかオフライン復旧で戻す）。
- アンカーに接続できない間に起動すると、全アカウントがサインインできません（再起動が必要）。
- ブロック中のアカウントに正しいパスワード（多くは置き換え前のもの）を入れると「変更が完了していない」と表示されます。
  そのパスワードが正しいことは分かりますが、サインインはできず、失敗回数として数えます。
- Web UI に管理者リセットのボタンはまだありません（API のみ）。
