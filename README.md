# Vulnix（ヴァルニクス）

**Find. Prove. Secure. — AI Security Testing Platform**

**AI は提案する、実行はゲートウェイが裁く（AI proposes, Gateway disposes）** を第一原則とする、AI セキュリティ診断・実証プラットフォーム（旧称: Aegis AI）。

AI/エージェント（ARTEX / Abliteration AI）の出力は常に「信頼できない提案（データ）」として扱い、実行権限はサーバ側シークレット（HMAC トークン）を握る Gateway だけが持ちます。バナー検知（`detected`）と正式な人間承認下の再現証明（`proven`）、そしてパッチ適用後の再検証（`not_reproduced`）を明確に分離し、無認可・破壊的な攻撃は一切行いません。

> 🛡️ **スコープと安全性**: すべての診断・再現検証ワーカー（`http_probe`, `reproduction_probe`, `demo_verify`）は Gateway が DNS ピン留めした許可ターゲットに対し、プロセス内 `egress_sentinel`（`socket.connect` ホワイトリスト強制）下で非破壊・読み取り専用のリクエストのみを実行します。

## アーキテクチャ

```
┌──────────────────┐   提案(untrusted)   ┌──────────────┐   権限あり   ┌──────────┐
│ ARTEX Engine ×   │ ─────────────────▶ │ ProposalRouter│ ──────────▶ │ Gateway  │ ─▶ Worker
│ Abliteration AI  │   schema に正規化    │ (権限を持たない)│   token 発行  │ (6層制御) │   (egress_sentinel)
│ (OpenAI互換API)   │   authority鍵を除去  └──────────────┘             └──────────┘
└──────────────────┘
```

- **ARTEX Engine × Abliteration AI**（`aegis/router.py`） …
  - `AbliterationBackend`: OpenAI 互換 Chat Completions API（`messages` / `choices[0].message.content` + Markdown JSON コードブロック抽出）に対応した専用アダプター。提案生成（`propose()`）と診断コンテキスト連携 Q&A（`chat()`）を提供。
  - `ArtexEngine`: 診断フェーズごとのタスク計画（`recon` → `header_audit` → `cve_match` → `verification` → `defense_verify`）を管理。実行権限は一切持たず、すべての提案を `ProposalRouter` に送る。
- **ProposalRouter**（`aegis/router.py`） … 実行権限を一切持たない（`tokens`/`approvals` 属性を持たないことをテストで保証）。提案を strict schema `{tool, target_id, action, args, rationale}` に正規化し、権限詐称キーを除去して Gateway に転送するだけ。
- **Gateway**（`aegis/gateway.py`） … 唯一の実行権限保持者。6層制御を通過した提案のみ、発行済みトークンと照合して実行。

### 6層制御モデルと P0 実機セルフテスト（`aegis/control_verification.py`）
1. 認可（Authorization） 2. ポリシー（Policy） 3. ネットワーク（Network）
4. ランタイム（Runtime） 5. データ（Data） 6. 緊急停止（Emergency）

`GET/POST /api/system/verify-controls`（UIの設定画面または診断コンテキストパネルから実行可能）により、実機の Worker サブプロセス・ソケット・ProposalRouter・Gateway を使って以下の 5 項目をエンドツーエンドで実機検証できます：
1. **許可外通信の強制遮断（`egress_isolation`）**: `egress_sentinel` 下で許可 IP:Port への通信が成功し、スコープ外 IP:Port（`198.51.100.99:4444`）への `socket.connect` が `PermissionError` で即座に遮断されること
2. **権限逸脱・詐称キー無効化（`privilege_escalation_prevention`）**: AI 提案に `approved: true` / `token: "forged"` を注入しても `ProposalRouter` が除去し、スコープ外 URL を Gateway が拒否すること
3. **L2 人間承認ゲート（`l2_approval_gate`）**: 承認なしのトークン発行が `ValueError` で拒否され、承認者の署名後のみ発行されること
4. **緊急停止 SIGKILL（`emergency_stop_sigkill`）**: 実行中の Worker プロセスグループが `kill_all()` により SIGKILL で即座に強制終了されること
5. **OS ファイアウォール構文検証（`netfilter_ruleset`）**: `nftables` default-drop ルール生成とホスト環境（Linux+root でのカーネル適用可否）の正確な報告

## 必要要件

- **バックエンド**: Python 3.10+（標準ライブラリのみ。外部依存なし）
- **フロントエンド**: Node.js 18+ / Next.js（`web/`）
- テスト確認環境: Python 3.15 / Node 26

## セットアップと起動

### 1. コントロールプレーン（Python）
```bash
python3 -m aegis.server            # http://127.0.0.1:8787 で待受
# オプション: --port 8787 --lab-port 18081 --verify-seconds 20 --data-dir ./data
```
- 初回起動時に操作者アカウントを生成し、**ハッシュのみ** `operators.json` に保存。平文の初期ログイン情報は `0600` 権限の別ファイルに出力され、パスはコンソールに表示されます。

### 2. Web UI（Next.js）
```bash
cd web
npm install
npm run dev                        # http://localhost:3000
```
`web/` は `/api/*` を `AEGIS_API`（既定 `http://127.0.0.1:8787`）へプロキシします。

### AI連携とデモの検証範囲

- 標準設定では内蔵の決定的な ARTEX プランナーと診断情報に基づく内蔵解説を使用します。外部モデルは起動時に設定した場合だけ利用します。
- `VULNIX_ABLITERATION_*` を優先し、`AEGIS_MODEL_*`、`VULNIX_MODEL_*` も利用できます。URL・キー・モデル名は同じ接頭辞で設定してください。別の接続先のキーを流用しません。
- OpenAI互換アダプターの提案形式・解説QAは単体テストとループバックHTTPサーバーで確認しています。これらは実モデルの推論品質やAbliteration済みモデルの実動作を保証するテストではありません。
- 既定の対象はローカルHTTP模擬ラボです。脆弱箇所・影響・対策・証拠を学び、模擬的な防御前後を比較できます。本番環境の自動修正・パッチ配布や、任意のサイトを対象にした万能のペネトレーションテストは実装していません。

### 実サービスの診断（所有確認済みの対象のみ）

管理権限を証明できた自社サービス（ステージング想定）だけを、次の順で診断できます。

1. **URL登録** — `POST /api/assets/challenge`。インストールごとに異なる検証トークンを発行します（この時点では対象へ通信しません）。
2. **所有確認** — `POST /api/assets/verify-ownership`。DNS TXT（`_vulnix-verify.<host>`）または `https://<host>/.well-known/vulnix-verify.txt`。失敗した再確認は確定済みの範囲を取り消します。
3. **範囲・禁止事項の確認** — `POST /api/assets/confirm-scope`。対象はそのホスト・そのポートのみ、30日で失効。ループバック／プライベート／メタデータアドレスへ解決されるホストは拒否します。
4. **L1診断（読み取り専用）** — GET 1回の実測から TLS・HSTS/CSP/nosniff・Cookie属性・CORS・公開技術情報（NVD/KEV照合）・未認証JSON応答を検査します。
5. **L2検証（任意・項目ごとの承認）** — 対象に判定ルール（サービスプロファイル）がある場合だけ候補が出ます。検証専用アカウントを `POST /api/assets/secrets` で暗号化保存し、承認責任者が項目ごとに実行します。一括検証や所有確認だけではL2は実行されません。

実サービスは自動登録されません。資産一覧に出るのは所有確認フローで登録したものだけで、削除した資産が再起動で復活することもありません。

所有確認と範囲確認の扱い:

- 範囲確認は、このインストールが発行したトークンに対する**証明の記録**（方式・ホスト・確認時刻）があり、それが24時間以内のものである場合だけ通ります。旧来の登録画面のチェックボックスや `ownership_verified` フラグだけでは通りません。
- IPアドレスは実サービスとして登録できません（ドメイン名のみ）。検証ファイルで所有確認した場合に診断できるのは https の443番ポートだけで、別ポートは DNS TXT が必要です。同じホストの別ポート・別スキームに登録し直すと、証明・範囲・保存済みトークンは破棄されます。
- 権限の根拠になる情報（所有証明の記録、確認済みの範囲、実サービスとして登録したホストの一覧）は、`state.json` 内でまとめて署名します（HMAC、鍵は `0600` のマスターキーから導出）。画面に出る資産の記録は表示用で、権限の判断には使いません。署名が合わない・無い場合は権限を一切復元せず、所有確認からやり直しになります。ループバック向けのテスト用スイッチは再起動で引き継ぎません。
- 署名には世代トークン（連番＋乱数）を含め、最新のトークンを別ファイル（`authority.epoch`、`0600`）にも記録します。取り消しや削除の前に保存した古い `state.json` を戻しても、世代が合わないため権限は復元されません。乱数を含むので、操作を繰り返して同じ世代を作り直すこともできません。`state.json` が無い・壊れている場合も世代は引き継ぎます。
- 取り消し（所有確認の失敗、削除など）を保存できなかった場合、ディスクに残った古い状態が再起動後に受け付けられないよう、使える手段を順に使います。(1) 世代の記録ファイルを消す。(2) 消せなければ中身を空にする。(3) それもできなければ、データディレクトリの**外**（`~/.vulnix/revocations/` と一時ディレクトリ。`VULNIX_REVOCATION_MARKER_DIR` で1か所に変更可）に、古い世代を名指しした署名付きの記録を残す。起動時にこの記録が見つかると、保存されていた所有確認・範囲確認は引き継ぎません（自分のものなのに読めない・署名が合わない記録も同じ扱いです）。
- 起動時にデータディレクトリへ書き込めない場合は、保存されていた権限を引き継がず、保存できるようになるまで実サービスへの送信をすべて拒否します。`state.json` を読み取れない場合も権限は引き継ぎません（元のファイルは `state.unreadable-<時刻>.json` として残します）。
- 残る限界: データディレクトリにも、上記の記録先にも書けない状態で取り消しが起き、その後書き込み可能に戻ってから再起動した場合は、取り消し前の状態に戻ります。記録先が「書けない」には、ディスクの障害のほか、**他のアカウントが所有するディレクトリは使わない**こと（共有の一時ディレクトリに同名のディレクトリを先に作られた場合など）、一時ディレクトリの記録が OS の掃除で消えることも含みます。確実にしたい場合は `VULNIX_REVOCATION_MARKER_DIR` に、データディレクトリとは別のディスク上の自分専用ディレクトリを指定してください。このときは監査ログに `state.revocation_not_durable` が残り、画面には「状態をディスクに保存できません」が出続けます（その間、同じプロセスは実サービスへの診断の送信も、所有確認の参照・取得も、範囲確認も行いません）。状態・世代の記録・取り消しの記録は、ファイルとディレクトリを同期（fsync）してから次へ進みます。（データディレクトリ全体を同時に巻き戻せる相手は、マスターキーを読める相手と同じ権限なので対象外です。）
- 結果を保存できなかった診断は「完了」になりません。一括・項目単位のどちらでも、保存に失敗した時点で状態は「失敗」になり、原因の種別（`persistence`: 保存の失敗 / `run`: 実行の失敗）と理由をスナップショットの `failure` に記録して画面に表示します。次に正常に終わった実行で消えます。
- 一度実サービスとして登録したホスト名は、所有確認が失効しても、資産を削除しても、模擬ラボの対象としては登録できません（実サービスとしての再登録はできます）。
- 起動時に、証明も確認済みの範囲も無いホストの検証用トークンが残っていれば消去します。
- 範囲の有効期限は診断開始や再検証では延長されません。

#### L2判定ルール（サービスプロファイル）

対象APIに固有の内容（適用ホスト、パス、応答マーカー、拒否ステータス、応答フィールド、どのアカウントがどの役割か、指摘事項の文面）はプロファイル（JSON）に置きます。汎用エンジン（`aegis/l2_rules.py`）、Gateway、Worker にはサービス名・パス・マーカーを書きません。読み込み順は次のとおりで、後のものが同じ `id` のプロファイルを置き換えます。

1. `aegis/l2_profiles/*.json` — リポジトリ同梱のひな形（公開してよい内容のみ）
2. `<データディレクトリ>/l2_profiles/*.json` — 導入先ごとの確定済みルール（git管理外。非公開のホスト名やAPIの根拠はここに置く）
3. 環境変数 `VULNIX_L2_PROFILE_DIR` のディレクトリ

同梱の `aegis/l2_profiles/deepnote.json` は適用ホストが空で全項目が `placeholder` のひな形です。これだけでは何も実行されません。プロファイルの `applies_to.hosts` に一致しない対象は L1 のみです。

各チェック（IDOR／共有リンク／ストレージACL／AIチャット分離／課金プラン）は独立したルールで、次を必ず定義します。起動時に検証し、満たさないルールは読み込みを拒否します。

| 項目 | 意味 | 読み込み時の制約 |
| --- | --- | --- |
| `spec_status` / `spec_evidence` | 対象APIの仕様と照合済みか、その根拠（定義ファイルと行番号など） | `confirmed` は根拠が必須。無指定は `placeholder` |
| `preconditions` | 同じ実行内で成立を確認する前提（対照） | 対象アカウント自身のトークンが有効だと示す前提が必須。対象と同じパスを別アカウントで取得できる前提（所有者対照）も必須で、無い場合は `owner_control_exception` に理由を書く。いずれも 2xx かつ応答内容の条件が必須 |
| `denied` | 権限外アクセスが拒否されたとみなす条件 | 4xx のみ。401・407・408・429 は不可。所有者対照が無いルールでは 404 も不可。`exposed` のマーカーが応答に無いことが必須 |
| `exposed` | 境界が破れているとみなす条件 | 2xx かつ所有者側データのマーカーが必須 |

判定と実行の原則:

- **`placeholder` のルールは実行できません。** 候補として一覧には出ますが、サービス層・シークレット保管（そのルールでしか使わないトークンは保存を拒否）・Worker への環境変数・Gateway のツール定義のすべてで拒否します。画面の警告だけに依存していません。
- HTTPステータスだけでは「再現せず」にしません。前提がすべて成立し、対象リクエストが `denied` のステータス**と**内容条件を満たし、応答が所有者の正常応答と同一でなく、応答全体を読み切れた場合だけ「再現せず」です。
- 前提を1つでも確認できなければ、権限外アクセスのリクエスト自体を送らず「未完了・要確認」にします。
- **L2 に承認責任者が必要かどうかは、実行対象を固定したあとにサービス内部で判定します**（HTTP 層の事前チェックだけに頼りません）。対象の切り替えと検証要求を同時に繰り返しても、操作者ロールでは実行されません。
- 模擬データのパスは、プロファイルが `override_pattern` で許可した形式にだけ変更できます（許可が無いパスは変更不可）。保存済みの変更値も、トークンを渡す直前にもう一度照合します。`override_pattern` は正規表現ではなく限定した書式です：固定の文字列に、可変部分 `[A-Za-z0-9_-]{m,n}`（文字種は `A-Z`・`a-z`・`0-9`・`_`・`-` をこの順で書いたものだけ、繰り返しは 1 以上 300 以下）を入れ、可変部分の直後は区切り（`/ = & : ~ ,`、`\.`、`\?`）か末尾にします。ワイルドカード、省略可能な部分、グループ、否定の文字クラスは使えません。
- 判定できなかった再実行は、以前の「実証済み」を取り消しません（修正未確認のまま残ります）。逆に、以前の「再現せず」は判定できなかった再実行のあとには維持しません。判定できなかった L2 検証は総合リスクを動かしません。
- Workerが実行したルールのSHA-256を証拠に含め、制御側は設定中のルールと一致する結果だけを採用して独立に再判定します。
- どのルールを実行するかは保存された指摘事項の記録ではなくプロファイルが決めます。模擬ラボ専用の検証は実サービスには実行できません。
- トークンは該当ルールが使うものだけを、その1回のWorkerプロセスの環境変数に渡します。平文（http）の対象には送りません。argv・監査ログ・`state.json`・レポート・動画用JSONには残さず（表示は SHA-256 先頭8桁の指紋のみ）、応答に含まれていた場合は証拠を切り出す前に全体から消します。役割の異なるアカウントに同じトークンは設定できません。
- 承認は1項目・1回の実行ごとに発行し、実行後に破棄します。
- 未計測のL2候補は総合リスクに加点も減点もしません。
- `GET /api/assessments/<id>/remotion` は、公開できる動画用JSONを返します。**許可リスト方式**で組み立てており、含まれるのは列挙値（深刻度・判定・状態）、数値、真偽値、証拠ハッシュの先頭16桁、このモジュールが持つ固定の文言だけです。診断結果の文章（タイトル・要約・URL・モデルの出力・対象の応答）、識別子（資産ID・指摘ID・担当者名）、日時は一切コピーしません。指摘の名称は組み込みの対応表から引き、プロファイル定義の指摘は「認可・アクセス制御の検証項目」という一般名になります。L1 の実測結果を L2 の再現確認とは表示しません。識別情報を含む完全版（`?anonymize=0`）は承認責任者または管理者だけが取得でき、監査ログに残ります。

#### アカウント・ロール・読み取り認証

| ロール | できること |
| --- | --- |
| `operator` | 診断の開始・停止、実サービスの新規登録（トークン発行と所有確認）、L2検証の実行依頼 |
| `approver` | 上記に加え、診断範囲の確定、検証用アカウントの設定、L2検証の承認・実行、修正後の再検証、所有確認済みの対象の削除・再登録 |
| `admin` | アカウントへのロール付与・剥奪（設定 → アカウントとロール、`POST /api/operators/roles`） |

- **アカウントは管理者が作成します。** 「設定 → アカウントとロール」（`POST /api/auth/register` を管理者のセッションで呼ぶ）で作成でき、作られるのは常に `operator` です（`roles` を付けても無視し、監査ログに記録）。未ログインでの自己登録は開発モード（`AEGIS_ENV=development`）でだけ使えます。誰でも届くポートから自分用のアカウント（＝読み取り権限と「別人」の身元）を作れてしまうのを防ぐためです。
- **ロールは自分では付与できません。**`approver`・`admin` は管理者が付与し、変更はすべて監査ログ（`operator.roles_changed`）に残ります。自分自身のロールは変更できず、最後の管理者から管理者ロールは外せません。ロールの剥奪はログイン中のセッションにも即時に反映されます。
- 初回起動時に `operator`・`approver`・`admin` の3アカウントを生成します。管理者ロールが無い既存の導入先では、起動時に管理者アカウントを1つ作成し、パスワードを `operators.admin-credentials.txt`（`0600`）に書き出します（既存アカウントは昇格させません）。以前に自己登録で承認責任者になったアカウントはそのまま残ります。管理者による付与記録が監査ログに無い承認責任者は、「設定 → アカウントとロール」に「要確認」と表示されるので、外すか、「このまま認める」で確認の記録を残してください。
- **実サービスの L2 は、カーネル隔離を確認できる Linux ホストでだけ実行します。** 検証用トークンを持つ Worker は、その1回の実行のために作った cgroup v2 と nftables のルールの中で起動します。ルールは、その cgroup のソケットから出る通信のうち、固定した宛先 IP:ポートへの新規 TCP と、その cgroup 自身が開始した接続の続きだけを通し、ほかは破棄します（IPv4/IPv6、UDP、ICMP、ループバックの他ポートを含む）。起動前に、同じ手順で起動した確認用プロセスが (a) その cgroup に入っていること、(b) 文書用アドレス（198.51.100.1）への接続に失敗すること、(c) カーネルの破棄カウンタが増えたこと、を確認し、1つでも確認できなければ Worker を起動しません（トークンも読み出しません）。実行後にルールが残っていなければ結果を破棄します。cgroup 内のプロセスを終了できなかった場合はルールを残したままにし、監査ログに `confinement.leftover` を記録します。Worker は root では動かしません（コントロールプレーンが root の場合は sudo の呼び出し元、なければ `nobody` に落とします）。`nft`・`sh`・`sudo`・`setpriv` はシステムのディレクトリからだけ探し、`PATH` には従いません。macOS / Windows など Linux 以外、または root（もしくはパスワード不要の sudo）・`nft`・`setpriv`・cgroup v2・`cgroup.kill`（Linux 5.14 以降）が無い Linux では、実サービスの L2 は常に拒否されます。これを切り替える設定や API はありません。**この隔離が防ぐのは Worker からの IP 通信の宛先だけです。** UNIX ドメインソケット（同じユーザーのデーモン、D-Bus、名前解決サービスなど）は対象外で、同じユーザーの権限で動く Worker が悪意を持って cgroup の外へ出る手段（ユーザーの systemd への依頼など）までは塞ぎません。サンドボックスではなく、自前の Worker が宛先を誤らないための OS 側の歯止めです。異常終了時に残った `aegis_l2_*` の cgroup / テーブルの自動掃除はありません。読み取り専用の L1 と同梱ラボの検証はこの隔離の対象外で、従来どおりプロセス内の制限で動きます。
- **実行者と承認者の分離（任意）**: `--separate-l2-approver`（または `AEGIS_SEPARATE_L2_APPROVER=1`）を付けると、実サービスの L2 検証は「ある操作者が実行を依頼し、別の承認責任者が承認して実行」の2段階になります。依頼した本人は承認できず、自己登録のアカウントは依頼できません。依頼は1回の実行で消費され、24時間で失効し、再起動後は引き継ぎません。この設定では修正後の再検証は L2 を自動で再実行しません。
- **読み取りAPIは既定でログインが必要です。** セッションなしで応答するGETは `/api/auth/me` と `/api/health` だけです。資産一覧・診断スナップショット・ログ・レポート・イベントストリーム・検証用アカウントの状態などは 401 を返します。以前の「未ログインでも読める」動作は**開発モード専用**です。`AEGIS_ENV=development` を設定したうえで `--no-read-auth`（または `AEGIS_REQUIRE_READ_AUTH=0`）を指定した場合だけ有効になります。開発モード以外で指定すると起動を拒否し（プログラムから組み込む場合は環境変数を無視して認証必須のまま動作）、有効化した事実は監査ログ（`config.read_auth_disabled`）に残ります。本番運用では使用しないでください。アカウント一覧（`/api/operators`）はこの設定に関係なく管理者専用です。

#### 外部モデル・プランナーとの連携範囲

- **対象を切り替えると、診断結果と証拠は必ず消去します。** 診断の実行中・一時停止中は対象を切り替えられません（先に停止します）。ある対象で取得した証拠が、別の対象のワークスペースに残ることはありません。
- 証拠には、取得した時点で取得元（模擬ラボ／実サービス）を記録します。外部モデルへ渡せるのは「模擬ラボで取得した」と記録された証拠だけで、実サービスの証拠や取得元が不明な証拠を含む指摘は、どの対象を開いていても送りません。あとから資産を削除したり同じ名前で登録し直したりしても、この記録は変わりません。
- 診断スレッドはワークスペースの世代に結び付いています。停止や切り替えで世代が変わると、古いスレッドは結果を一切書き込めず、要求も送れません。緊急停止も世代を終わらせます。項目単位の検証・修正後の再検証のスレッドも同じ扱いです。名前解決や所有の再確認で待たされていた要求は、Worker を起動する直前に、停止・リセット・範囲の取り消し・対象の削除や切り替えが起きていないことを確かめ直し、起きていれば送信しません。
- **実サービスに関する情報は外部へ送りません。** 外部モデル（`VULNIX_ABLITERATION_URL` など）や外部プランナー CLI を設定していても、実サービスの診断では内蔵プランナーと内蔵の解説だけを使います。対象のURL、検出結果、証拠（応答本文・Cookie など）、所有確認のトークン、担当者名は外部に出ません。外部モデルを使うのは模擬ラボのときだけで、チャットごとに監査ログへ `sent_to_external_model` を記録します。
- モデルの API キーを付けた要求は、https（ループバックのみ http 可）にだけ送り、リダイレクトは追いません。応答サイズに上限があります。
- プランナーやモデルの提案は実行権限を持ちません。設定検査フェーズで実行するのは固定の GET 1回だけで、それ以外の提案は「未実行」として記録します（実行済みとは表示しません）。
- 脅威情報は同梱のフィードを使います。`POST /api/cve/sync`（承認責任者または管理者）で渡した内容は再起動で消え、渡した内容のハッシュを監査ログに残します。

#### 対象サーバーの応答の扱い

- 応答ヘッダーなど対象が決められる文字列は、長さを制限し、制御文字・HTML タグ・Markdown のリンクやコードの記法を取り除いてから、タイトル・要約・レポートに使います。バージョン文字列の解析は入力長に対して線形で、極端に長い値でも診断や緊急停止を止めません。
- L1 の判定は実測した応答だけに基づきます。Cookie の属性は `;` 区切りの属性として解釈し、HSTS は `max-age` が正の値のときだけ有効とみなします。`Access-Control-Allow-Origin: null` と資格情報の併用は高リスクとして扱い、リダイレクト応答には文書用ヘッダー（CSP・nosniff）の指摘を付けません。http の対象には「HTTPS 未使用」を報告します。
- 既知の制約: TLS 1.2 未満しか話せない対象は接続自体が失敗し（指摘としては出ません）、CSP の内容の弱さ（`unsafe-inline` など）は評価しません。同名ヘッダーが複数ある場合は最後の値だけを見ます。

#### セッション・ログイン保護・検証ジョブ

- **セッショントークンは保存しません。** `sessions.json` とメモリに持つのはトークンの SHA-256 だけで、ロールも保存しません（ロールは毎回アカウントから読みます）。ファイルを読まれてもセッションは再開できません。旧形式（トークンを平文で保存）のセッションは移行せず、起動時に失効させて監査ログに記録します。該当の利用者はログインし直すだけです。
- **ログインの試行制限**: 同じユーザー名で15分以内に5回失敗すると、そのユーザー名でのログインを15分止めます（正しいパスワードでも不可）。認証コードの誤り、パスワード変更・2要素認証の無効化での誤りも数えます。存在しないユーザー名でも同じ応答（429 と `Retry-After`）を返し、照合にかかる時間も同じです。失敗の記録は、名前がアカウントかどうかに関係なく同じ規則で持ちます: 上限（5000 件）までは名前ごと、それを超えた名前は固定数の共有枠（鍵付きハッシュで振り分け）で数え、記録は時間の経過でしか消えません。大量の架空名を送っても、既存のカウンタは消えず、アカウントの有無も判別できません（共有枠では、まれに無関係な名前同士が同じカウンタを使います）。試行はパスワード照合の前に数えるため、並列に投げても評価される回数は増えません。数え方は入力されたユーザー名そのもの（大文字小文字・空白を区別）なので、`ROOT` や ` root` を連打しても `root` はロックされず、似た名前のアカウントで他人のカウンタを消すこともできません。認証コードは一度使うと再利用できません。
- **正当な利用者の復旧手段**: 15分で自動解除されます。急ぐ場合は管理者が「設定 → アカウントとロール」（`POST /api/operators/unlock`）で解除できます。管理者自身がロックされた場合は、このマシンの利用者が `operators.json` と同じディレクトリに `unlock.request`（1行に1ユーザー名、権限 `0600`）を置くと、次のログイン試行時に1回だけ解除されます。ロック状態はメモリ上だけなので、コントロールプレーンの再起動でも解除されます。認証アプリを失くした場合は、別の管理者が2要素認証をリセットします（`POST /api/operators/reset-mfa`、対象の全セッションを終了）。いずれも監査ログに残ります。
- 2要素認証の無効化には、パスワードと現在の認証コードの両方が必要です。
- **検証ジョブの起動は POST のみ**です（`/api/system/verify-controls`、`/api/cve/real-software-verify`）。承認責任者または管理者のロール、CSRF ヘッダー、許可されたオリジンが必要で、開始・拒否を監査ログに記録します。GET は 405 を返します。プランナー接続確認（`/api/router/verify`）と脅威情報の同期（`/api/cve/sync`）も承認責任者または管理者が必要です。
- **ループバック以外の名前では応答しません。** コントロールプレーンは `Host` が `127.0.0.1` / `localhost` の自ポートでない要求を 421 で拒否します。Web UI も `127.0.0.1` で待ち受け（`npm run dev` / `npm start`）、API プロキシは `Host` と `Origin` がループバック名のときだけ中継します（別名で公開する場合は `AEGIS_UI_ALLOWED_HOSTS` に明示）。拒否した要求のあとは接続を閉じ、読み残した本文が次の要求として解釈されないようにしています。
- 1つのデータディレクトリを使えるコントロールプレーンのプロセスは1つだけです（2つ目は起動を拒否）。状態を保存できない間は、実サービスへの診断を止めて画面と監査ログに表示します。保存できることは、実サービスへ要求を送る直前に毎回確かめます（診断の途中で保存できなくなった場合も、次の要求は送りません）。所有の再確認のための DNS 参照や検証ファイル取得も行いません。

#### 導入先プロファイルの保護

- `<データディレクトリ>/l2_profiles/` のファイルは、実行ユーザーの所有で、グループ・他者が書き込めないこと（ファイル `0600`、ディレクトリ `0700` を推奨）、通常ファイルであること（シンボリックリンク不可）を確認します。満たさないファイル、内容が不正なファイルは読み込まず、理由を画面と監査ログに出します。
- 読み込んだプロファイルは、**管理者がその内容（SHA-256）を承認するまで実行できません**（設定 → L2判定プロファイル、`POST /api/l2-profiles/accept`）。承認画面には、承認によって送信可能になるリクエスト（パス、使うアカウント、対照、拒否・露出の条件、仕様の根拠）と置き場所を表示し、確認のチェックを入れないと承認できません。承認は署名付きで保存し、承認後にファイルが1バイトでも変わると実行不可に戻して `l2.profile_changed` を記録します。起動のたびに、読み込んだ全プロファイルのハッシュを `l2.profiles_loaded` として記録します。
- 同梱のひな形は、適用ホストが無く実行可能なルールも無いため、承認の対象外です。

#### 所有確認時の名前解決と、解決先アドレスの変化

- 検証ファイルの取得は、名前解決を1回だけ行い、返ったすべてのアドレスが公開アドレスであることを確認したうえで、**確認したそのアドレスに**接続します（取得時に名前を解決し直しません）。証明書はホスト名で検証し、リダイレクトは追いません。NAT64・6to4・Teredo のように IPv4 を埋め込んだアドレスは公開アドレスとして扱いません。
- 所有確認はホスト名に対する証明ですが、通信はアドレスに対して行われます。診断のたびに、解決先に「まだ証明で確認していないアドレス」が含まれていれば、送信の前に所有の証明を取り直します（DNS TXT の再確認、または新しいアドレスからの検証ファイル取得）。確認できれば、そのアドレスを確認済みとして記録し（署名付き）、できなければ診断範囲を取り消します。確認済みのアドレスも24時間ごとに証明を取り直します。Worker は Gateway が検証したアドレスにだけ接続します。
- DNS TXT による証明はホスト名（DNS ゾーン）の管理を示すだけで、新しいアドレスの持ち主までは示しません（放置された DNS レコードの乗っ取りなど）。そのため、DNS TXT で確認した対象の解決先が変わった場合、読み取り専用の L1 は続行しますが、**検証用トークンを使う L2 は、承認責任者が所有確認と範囲確認をやり直すまで止めます。** 検証ファイルで確認した対象は、新しいアドレス自身からファイルを取得できた場合に限り、そのまま続行します。
- DNS TXT は、応答中の TXT 文字列がトークンと完全に一致した場合だけ成立します。

検証範囲: 上記はループバックの模擬サービスとテスト用プロファイル（`tests/fixtures/l2_profiles/example.json`）で確認しています（`tests/test_real_service.py`）。実在サービスへの通信は自動テストでは行っていません。
